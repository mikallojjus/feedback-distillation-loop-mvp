# claim-tagger-mvp: the claim tagger and its editor feedback loop

Read this first. It is the one runbook of this agent, written for the engineer; editors use the skill `/claim-tagger` and never need it. The repository's `CLAUDE.md` holds the hard rules, `docs/mvp-2026-11/CONTRACTS.md` the file shapes, `docs/mvp-2026-11/HUB-AND-GEO-CLAIMS.md` and `setup/structure.json` the Notion layout from 27 October 2026 (`docs/mvp-2026-11/STRUCTURE.md` is the approved proposal of 15 October, kept as history), `docs/mvp-2026-11/WORKLOG.md` the build log. The previous build in `agents/claim-tagger/` is read-only history, but this agent still imports eight small modules from its `scripts/lib/` (exit-codes, hash, jsonl, notion-values, pyjson, rng, stats, validate): that folder stays and is not edited.

## 1. What the agent is, and where it lives in Notion

The agent reads Geo claims from the Notion table Claims, asks a pinned Claude model which tags of the rulebook apply to each claim (in this build only Context-dependent has rules), writes its answer on the claim in eight columns of its own (Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Agent reading), and lists every claim that waits for an editor in the view Your queue of that table, where an editor decides it in three columns: Verified tags, Review status and Challenged tags notes (`docs/mvp-2026-11/CLAIMS-REVIEW.md`; from 22 October the editor no longer fills Why wrong, decision P4 and `docs/mvp-2026-11/READ-DECISIONS.md`). A second table, Tag decisions, is the agent's own ledger of what it proposed, what the editor decided and how the agent read the decision; editors never write to it. Where an editor decided a tag differently from the agent's proposal, the agent reads the disagreement itself (Agent slip, Rule unclear or Rule should change, the rule it points at, one line of why), turns the readings that point at a rule into proposed rule changes, tests an approved change with a safety check, and only after a PASS writes the new rule into the Rulebook and saves a new edition of the rulebook. Nothing is ever appended to a prompt: the rulebook text is the only thing that learns, and it learns only from decisions people made (decision P8).

Claims is the one claims table (decision P5) and the real training table: 200 Geo claims tagged Debate, picked from six Geo spaces by `scripts/geo-pick.mjs` and seeded once by setup (decision P6). Every decision an editor makes there is training data.

Needs: Node 22 or later, the `claude` CLI on the subscription (no API key), `NOTION_TOKEN` in `.env` (git-ignored; never opened, printed or sent anywhere), and the Notion integration connected to the hub page. Geo needs no key: it is read with queries only, through `scripts/lib/geo-read.mjs`.

Everything sits under the Notion page "Claim tagger", the hub (`3fa273e214eb805199f3d12ef01db453`; until 27 October 2026 it was called "Feedback Distillation MVP"). Its body holds one line of warning, "Claims is the real table: every decision you make there trains the rulebook. To practise, open Onboarding." (decision P14), and then only links: Your queue, Needs your note and Lessons waiting at the top, then the five tables, each a full-page table with a line of description under its name, then the sub-page Onboarding and the archive page (decisions P10 and P11). The ids are in `config.json`, which setup fills; between the archive step and the fresh build the table ids read `<setup>`.

The three views of Claims are lean (decision P15; Agent confidence is still the sort of all three, lowest first, and no view shows it): Your queue shows Geo Name, Tags waiting, Agent reasons, Agent tags, Verified tags, Challenged tags notes and Review status; Needs your note shows Geo Name, Verified tags, Agent reading, Challenged tags notes and Review status; Agent disagreed shows Geo Name, Agent reasons, Agent reading, Verified tags, Challenged tags notes and Review status. The other columns stay in the table, hidden, and the editor's columns come in the order the editor fills them, Review status last, so no row vanishes half filled (decision P13). The table's own view (the one Notion makes with the table) is arranged too and stays the first tab, so that clicking a table on the hub opens it (`default_view` in `setup/structure.json`, decisions 104 and 107: the build makes the named views after it, in the structure's order; a view made without its place, or a table built the other way round, needs the tab dragged to the front by hand, and `verify` cannot see the order because the views API does not document the order it lists views in): Claims calls it "All claims" and shows Geo Name, Geo Space, Agent tags, Agent status, Verified tags, Review status and Geo URL (Geo ID, Geo Created, Geo Sources, Geo Is factual, Geo Tags and Geo Topics are hidden there; decision P12); Rulebook calls its own view "Rulebook" (it has no other view, decision 108) and shows Name, Category, Status, When to use and Example Claims; Rule changes shows Lesson, Tag, Status, Current text, Proposed text and Safety check result; Tag decisions shows Claim, Tag, Agent proposal, Tag outcome and Agent reading; Agent settings shows its four columns. Claims has no "(old)" columns. Your queue lists the claims whose Agent status is Waits for you and whose Review status is not Reviewed, lowest confidence first (a new claim has no Review status, so the filter is sent as "is not Reviewed, or is empty", decision 106): a claim leaves it the moment the editor sets Review status to Reviewed (decision P13) and keeps Waits for you in Agent status until the next tag run reads the decision; Needs your note lists the claims whose Agent reading contains "without your note" (a disagreement the agent read with no note from the editor; the view lists a claim only once distill has written its Agent reading, while `status` counts it at once); Agent disagreed lists the claims whose Agent status is Disagrees with your decision. The two ledger views show the reading columns (Agent reading, Rule, Reading note, Read under) after Your reasoning, and Needs your note (ledger) filters on Reading note contains "without your note". Reports link the views through `config.json` `notion.views`; the table's own link is the fallback, and until `setup.mjs views` has run there is no view key.

Sub-pages of the hub: **Onboarding** (`notion.pages.onboarding`), where every practice page goes, one per walkthrough run, never deleted; and the **archive**, "Feedback Distillation MVP (archive, to 27 Oct 2026)" (`notion.pages.archive`), whose first line links back to the hub. The archive holds the first build of 15 to 22 October: Structure proposal, Demos (the calibration pages and the product owner's practice page), Demo tests (the skill's eval pages and the verification runs) and the five tables of that build, among them the 50-claim Claims copy and the Rulebook copy. Everything in it is protected and read at most (section 6). At the fresh setup the tables hold 13 Rulebook rows, the 200 claims of the pick, a decided ledger row for each audit claim that Geo still tags Debate, and 1 settings row. Read only and protected besides: the taxonomy "Claim Tags — verified" and the real "U.S. Politics debate claims". The old hub and sandbox under "Editorial feedback loop" are history.

## 2. Commands

Run from the repository root. `.claude/settings.json` lets Claude Code run the scripts below without asking, except `setup.mjs`, `geo-pick.mjs`, `rollback.mjs` and `restore.mjs` (it asks every time); `headless-check.mjs` and `transcript-check.mjs` have no rule, so it asks for those too. The loop scripts also take `--pull <pull-id>` (use that pull instead of pulling again), `--run-id <id>` and `--help`; `--driver fake` is for tests.

The loop, and what each step writes in Notion:

| Step | Who | Writes in Notion |
|---|---|---|
| Tag | editor types `tag` | Claims: Agent tags, Agent confidence, Agent reasons (one line per judged tag: the tag and the reason the ledger holds, so the editor sees why in Your queue), Agent status, Tags waiting, Agent edition, Agent remarks (never Agent reading). Tag decisions: a row for every judged claim and tag (a new row is unread), and on a Reviewed claim the copy of the decision. Agent settings: edition, Last run summary |
| Decide | a person, in Your queue (Claims) | Verified tags, Review status Reviewed, Challenged tags notes (the agent never writes these). A note line may open with a reason word (`Agent slip.`, `Rule unclear.`, `Rule should change.`) after the tag name; the agent then takes that reason as it stands |
| Distill | editor types `distill` | First it reads the decisions: Tag decisions gets the copy of any decision made since the last tag step and, on every disagreement (a Reviewed claim's judged tag whose outcome differs from the proposal, not marked Fixed), the reading: Agent reading, Rule, Reading note, Read under; Claims: Agent reading (one line per read tag). Then it drafts: Rule changes, one row per lesson from the readings that point at a rule, Status Proposed. Agent settings: Last run summary |
| Approve | the rule owner, a person, in Lessons waiting | Status Approved or Rejected, Editor wording (the agent never writes these) |
| Promote | editor types `promote` | PASS: Rulebook (When to use), Rule changes (Live, result), Agent settings, and a new committed edition in `rubric/`. FAIL or HOLD: only the result and Agent settings |
| Follow-up | by itself after a PASS | Tag decisions: Follow-up (Fixed or Still wrong). Claims: the agent's columns of those claims (Agent tags is the editor's set on a Reviewed claim; Agent status is Disagrees with your decision where the agent still differs; Tags waiting, Agent edition, Agent remarks, and Agent confidence where every judged tag was checked again) |

**What distill does first: it reads the decisions** (decisions 64 to 73, `CONTRACTS.md` section 17). After bringing the ledger's copies up to date, distill sorts every judged tag of every Reviewed claim. An agreement has nothing to read (the claim's Agent reading says "Nothing to read: the agent agreed with you."). A row marked Fixed is never read again. A row whose Read under (`<edition> · <hash8>`: the hash over the outcome, the proposal, the note line, the reason word and the edition the proposal was made under) is current keeps its reading and costs nothing. A stale row whose note line opens with a reason word is taken as it stands, with no model call: the rule the note names (else the rule the agent cited) and the note "Your note says so.". Every other stale row goes to the model (`models.distill` at `distill.reading_effort`, medium; `prompts/reading.md`) in batches of `distill.reading_batch` (10), two attempts per batch, each refused reply kept as `rejected/reading-batch-<n>-attempt-<k>.md`; a batch that fails twice leaves its rows unread this run and the next run tries again. A disagreement with no note at all is still read, and flagged in code, never by the model: its Reading note opens with "without your note" and the claim's line carries ", without your note", which is what Needs your note filters on. A note line that names a rulebook tag the agent did not judge gets the line "<Tag>: the agent did not judge this tag, so nothing to read." A promote alone makes no reading stale (decision 66 as amended on 22 October); a tag run or the follow-up that proposes again under the new edition does. The lessons are then drafted from the rows read Rule unclear or Rule should change, grouped by tag and the reading's rule (else the rule the agent cited), Fixed rows left out, at least `distill.min_claims` claims per group; Agent slip rows draft nothing and may be counter-evidence; a reading of a decision without a note (decision 78) is the agent's guess: it drafts nothing and is no counter-evidence either until the editor writes a note; the lesson's Kind is derived (Change the rule when any row of the group reads Rule should change, else Clarify wording). The report: "Distill: read N of your decisions and drafted one rule change from M of them." (M is the number of decisions the rule change rests on; or "Distill: read N of your decisions; no rule change to draft; <why>.", with "; M could not be read this time" when a batch failed, and "; K of your decisions have no note and wait in Needs your note" while some decision has none), a table of Read, Point at a rule (readings that blame the rule and rest on a note), Agent slips, Without a note and Rule change (the counts of this run), and a Next line: reject a rule change that rests on a decision the editor now calls the agent's slip (decision 79: "the rule change "<title>" rests on a decision you now call the agent's slip" in the sentence, nothing new drafted for that rule meanwhile, promote holds with exit 10, the follow-up marks only rows that still point at a rule, and only the editor sets Rejected); else Lessons waiting when a lesson was drafted; else approve or reject (a rule change is Proposed) or promote (Approved); else Needs your note when a disagreement has no note; else status. Distill exits 2 only when something was to read, nothing could be read and no rule change was drafted (or every reply of a lesson group was unusable).

**The status row "Your decisions"** (decision 74). Three counts of claims, made from the ledger the way distill brings it up to date, over Reviewed claims with a disagreement row that is not Fixed: `<n> to read` (a row never read or stale, a reason word distill has not written yet included), `<n> points at a rule` (`<n> point at a rule` from two: a current reading of Rule unclear or Rule should change with a note of the editor's, decision 78; Still wrong stays open) and `<n> without a note` (neither a reason word nor words for the tag, read yet or not). The row sits between Your queue and Lessons waiting, shows the parts that are not zero ("3 to read, 1 without a note") and is left out when all three are zero; the old "Needs your note" row is gone. `status --json` holds them as `queue.to_read`, `queue.pending_rule_decisions` and `queue.needs_note`, and the claims the agent has not read yet (not Reviewed, Agent status empty) as `queue.unread`. The Next line is the first that applies: an unread claim (practice page only: the demo tag command); start at the top of Your queue, or decide the claims there; claims the agent has not read yet (production only: "Next: type /claim-tagger tag to read N new claims."); distill, while something is to read or at least `distill.min_claims` claims point at a rule, and no rule change is Proposed or Approved; reject a recanted rule change (the Lessons waiting row then says "1 rule change to reject (rests on a decision you now call a slip)"); approve or reject; promote; tag. With nothing in Your queue and no rule change the sentence follows the row: "nothing is paused; the agent has N of your decisions to read." or "...; N of your decisions have no note." In production, when nothing else is to say, the sentence is "nothing is paused; the agent has N new claims to read." The row Your queue counts exactly what the view lists, the claims that are Waits for you and not Reviewed ("<n> rows, lowest confidence first", else "nothing waits"), and, in production, ends with the claims the agent has not read yet ("nothing waits; N new claims not read yet"); a claim leaves the view the moment it is Reviewed, so a decided claim the agent has not read yet is told in the row Your decisions ("<n> to read"), never in Your queue (decision 101; `queue.decided_listed` in `--json` still counts the claims decided since the last tag run).

The skill relays the report verbatim first. When the report's Next line sends the editor to Notion (after `tag`, `distill`, a `promote` that ended in FAIL, a `follow-up` that left claims in Agent disagreed, `status` when it says to decide or approve, and the demo variants of these), it adds one checklist of at most five lines below the report: which view to open, which columns to fill in and in which order, what to look at, and the next command to type. The checklists are in `.claude/skills/claim-tagger/references/guide.md`, in the words of the practice page (same column names, same order); the walkthrough skill uses the Demo forms after a demo command and `walkthrough.mjs where`. ## 3. Setup: the archive and the fresh set (from 27 October 2026)

Engineer only; every `setup.mjs` and `geo-pick.mjs` call asks for permission. The plan is `docs/mvp-2026-11/HUB-AND-GEO-CLAIMS.md` (decisions P5 to P12). Every step is safe to run again with the same arguments: rows are matched by key and a key already in the table is skipped; pages and tables are matched by the id in `config.json` and then by title under the hub, but a table that is protected or listed in `setup/archive.json` is never adopted by its title (decision 85); `canaries` refuses to overwrite a different file. A create whose answer was lost (`create_uncertain`) is never sent twice; run the step again and it finds the object. In order:

1. **Everyone pulls first.** The product owner tells the editors who have their own checkout to stop and pull (`docs/mvp-2026-11/EDITOR-HANDOVER.md`): an older checkout still names the old tables in its `config.json` and would write them.
2. **The Geo pick** (Geo only, no Notion): `node agents/claim-tagger-mvp/scripts/geo-pick.mjs --seed claims-2026-10-27 --audit agents/claim-tagger-mvp/setup/audit-decisions.json`. It reads Geo through `lib/geo-read.mjs` (queries only, no credentials, `https://api-testnet.geobrowser.io/graphql`, the `geo` block of `config.json`) and picks 200 claims tagged Debate by space quota: U.S. Politics 50, World affairs 50, AI 40, Health 30, Crypto 20, Technology 10; a space with too few passes its gap to the others in turn. Inside a space the claims are spread over the UTC months they were created in, and a seeded shuffle picks within each month. The audit claims that Geo tags Debate are forced in; the others are left out and named with the reason. It writes `setup/geo-claims-pick.json` (`schemas/geo-pick.schema.json`: the populations, the allocation, the duplicates set aside, the audit's included and left-out claims with the audit file's sha256, the Geo Tags names, one row per claim with the lean Geo columns) and `runs/geo-pick/<run-id>/` (report and a request log with no bodies). The same seed and the same Geo data give the same file; an existing pick is never overwritten without `--replace`. Exit 1 means Geo could not be read: run the same command again. The pick is committed, and the options of Geo Tags (its `tag_names`) and Geo Space (`config.json` `geo.spaces`) are set from it before the first build: `node agents/claim-tagger-mvp/scripts/setup.mjs structure --options-from agents/claim-tagger-mvp/setup/geo-claims-pick.json` (files only). The old inputs `setup/claims-pick.json`, `claims-pages.json` and `rulebook-pages.json` move to `setup/archive-2026-10/` with `git mv`; the tests that used the 50-claim pick read `tests/mvp/fixtures/claims-pick.50.json` (decision 99), and none reads the three files from this folder.
3. **A builder session:** `node agents/claim-tagger-mvp/scripts/setup.mjs builder open --reason "P9: archive the first build, fresh set under the hub"` creates the marker `runs/SETUP` (one session at a time, a reason is required) and a line in `runs/builder/log.jsonl`. Every building step refuses without it.
4. **The archive** (decision P9; not part of `all`). `setup.mjs archive --plan-only` sends GETs only and prints the plan: rename the hub to "Claim tagger"; make the page "Feedback Distillation MVP (archive, to 27 Oct 2026)" under it, whose first line links back to the hub; move the eight old objects into it (the pages Structure proposal, Demos and Demo tests, and the five old tables); what is done already; and the blocks on the hub that are none of the eight. Read it, then `setup.mjs archive`. It does those steps and reads every new parent back (`POST /v1/pages/{id}/move` for a page, `PATCH /v1/databases/{id}` with only `parent` for a table). Then it walks the old tree (the practice pages under Demos and Demo tests with their tables and data sources, the old views) and writes `setup/archive.json` with state `done`. It rewrites `config.json`: pages `onboarding` (`<setup>` until the build makes it) and `archive`, the old page keys kept as `<archived>`, the five table ids back to `<setup>`, `notion.views` emptied, and every archived page, table and data source, practice pages included, added to the protected lists. Last, it sets `runs/builder/{pages,databases,state,verify}.json` aside under `runs/builder/before-archive/`. Commit `config.json` and `setup/archive.json`.
   - A move that Notion refuses stops with exit 2 and says what to do: drag it into the archive page by hand, then run `setup.mjs archive` again. Any other stop is exit 1: run the same command; it reads the parents first and does only what is missing.
   - After `done`, a run says "done already" and sends nothing.
   - Every other step that builds or writes (`pages`, `databases`, `views`, `hub`, `build`, `rulebook`, `claims`, `seed-audit`, `migrate-decisions`, `rubric`, `canaries`, `settings` and `all`) refuses with exit 2 while `setup/archive.json` says `moving`, and also while the file is missing and `config.json` still names the first build's tables: "the first build's tables are still on the hub page; run setup.mjs archive first (P9)"; and while it says `done` but `config.json` does not name the Archive page it made (the rewrite of the config failed after the record was written): "the archive step moved everything in Notion but config.json was not rewritten; run setup.mjs archive again (it sends nothing to Notion)" (decision 109). A fresh install, whose config holds placeholders for the tables, builds; so does an install whose builder state says its own build passed the gate (decisions 85 and 98). `preview`, `verify`, `structure` and `api-check` are not held back.
5. **A person** removes by hand any block on the hub that the archive step listed as a leftover. The step never touches them.
6. **Build and seed.** `setup.mjs preview` (5 tables, the lean Claims columns, 6 views, Onboarding and the hub links), then `setup.mjs build`, then `setup.mjs all --taxonomy agents/claim-tagger-mvp/setup/taxonomy-issue.json --claims agents/claim-tagger-mvp/setup/geo-claims-pick.json --audit agents/claim-tagger-mvp/setup/audit-decisions.json`. The build makes the five tables as full-page tables in the hub's order (Claims, Rulebook, Rule changes, Tag decisions, Agent settings; decision 86), each with its description, with their columns and relations, then Onboarding below them, then the views (made after the table's own view, which is arranged as the structure says and stays the first tab, decisions 104 and 107), then the warning line and the three link lines at the top of the hub (decisions 87 and 103); it reads Notion first and does only what is missing, so a second run writes nothing. Each id is written at once to `config.json` and `runs/builder/*.json`. The steps of `all`, each also alone, ending with `verify`:
   - `api-check`, `databases`, `pages`, `views`, `hub`: the build again; they find everything there.

## 5. Models and runs

| Work | Model | Effort | Prompt |
|---|---|---|---|
| Judge: every claim, the safety check's two rulebooks, the follow-up | `claude-sonnet-5-5` | medium | `prompts/judge.md` |
| Distill, first: the reading of each disagreement (batches of 10 rows; a note line that opens with a reason word needs no call) | `claude-opus-5-5` | medium | `prompts/reading.md` |
| Distill: lessons from the readings that point at a rule | `claude-opus-5-5` | high | `prompts/distill.md` |
| Wording sentence after a FAIL (30 words at most; report and `card.md` only, never Notion) | `claude-opus-5-5` | high | `prompts/wording.md` |

Every call is `claude -p` through `lib/claude.mjs`: no shell, the prompt on standard input, each claim quoted as data in a `<claim>` block, no tools, one turn. The pinned model must appear in the answer's model usage, else exit 4 and the answer is dropped. `--bare` and `--fallback-model` are refused in code. The previous build's fallback subagents were removed; no script of this agent calls a subagent.

**Adaptive runs.** Run 1 reads every claim once, in batches of `judge.batch_size`, `judge.concurrency` batches at a time. A cell (one claim, one tag) is unsure when the decision is `ask_editor` or its probability lies strictly between 0.25 and 0.75. Claims with an unsure cell are read again (run 2), at most 30% of the run's claims, least sure first; the rest are listed as `capped` in `run.json`. Run 3 happens only where runs 1 and 2 disagree. Answers already in the cell store are never asked again, so a repeat run asks nothing. `propose` then takes the majority of the reads (`ask_editor` wins a tie); a cell is unsure when a read failed, the reads disagree or the mean probability is inside the band, and each unsure cell without a row becomes a queue row.

**Error classes.** An invalid reply (not JSON, a claim or tag missing, a break of `schemas/judge-reply.schema.json`) gets one more attempt for its batch; after that the batch's claims are stored as errors, the next run tries them again, and this run ends with exit 2; each refused reply is kept as it came under the run's `rejected/` folder, with the problems listed, so that a batch that fails twice can be read. A transient error (429, overloaded, busy, timeout, any other failed call) waits `judge.transient.backoff_ms` and retries; the third in a row stops the run with exit 1 and its resume command. Only the CLI's usage-window wording stops a run with exit 75, nothing written for that batch; the window is checked first, so a 429 that says the limit was reached counts as the window.

| Exit | Meaning |
|---|---|
| 0 | ok |
| 1 | stopped: run the same command again (three transient errors in a row, a write that did not finish, Geo could not be read, an unexpected error) |
| 2 | invalid: usage, no token, a refused plan, a duplicate key, a read-back that differs, a batch that could not be read (distill: only when rows were to be read, none could be, and no rule change was drafted), a claims table without the agent's reading columns, a move Notion refused, a building step before the archive is done, a practice page in the archive |
| 3 | paused |
| 4 | drift (the rulebook text in Notion or the file on disk no longer matches the saved edition) or another model answered |
| 5 | not used by this agent; the shared table calls it trust breaker |
| 10 | HOLD: nothing to check a change against |
| 11 | FAIL: the safety check failed; the rulebook did not change |
| 75 | usage window (editors read "your Claude allowance ran out"): resume later |

## 6. Safety

The ten hard rules in `CLAUDE.md` apply; this is how they are kept here.

- **Plan before write.** A script that writes builds `plan.jsonl` first; nothing is sent before the plan is checked, and `--plan-only` stops there.
  - `checkPlan` (`lib/plan.mjs`) refuses the whole plan for: a table that is not one of the five in `config.json`; a column outside the table's allowlist; an editor column (below); a Status on a rule change other than Proposed, Live or Rolled back; a protected id in any string; a missing or repeated key.
  - `applyPlan` sends the ops in order through `lib/notion-rest.mjs` (paced at `requests_per_second`, with retries). It never moves anything: the client's two moves belong to the archive step alone, and the client has no call that deletes or trashes. It skips an update whose `expect` no longer matches the pulled value, appends one ledger line per op and reads every written page back.
  - Success is claimed only after the read-back: a difference is exit 2, a write that could not be read back is exit 1, and the next run re-reads, never re-writes.
- **Allowlist per table.** Tag decisions (the ledger): Claim, Key, Tag, Agent proposal, Agent confidence, Agent reason, Claim link, Rulebook edition, Follow-up, the copies of the editor's decision (Tag outcome, Why wrong, Your reasoning, Decided under) and the agent's reading (Agent reading, Rule, Reading note, Read under). Rule changes: Lesson, Tag, Rule, Kind, Current text, Proposed text, Safety check result, Supporting rows, Status. Agent settings: Rulebook edition, Last run summary. Rulebook: When to use. Claims: Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Agent reading. Only distill writes the reading columns; propose and the follow-up never write or clear them. A create at setup may fill every column of the table it seeds. The check is on columns, not rows: that propose never rewrites the proposal columns of a decided row or of a Reviewed claim's row, and that follow-up writes only Follow-up there, is the scripts' own rule.
- **Editor columns** are Verified tags, Review status and Challenged tags notes (Claims), Editor wording and the Status values Approved and Rejected (Rule changes), Paused (Agent settings). Tag decisions has none: Tag outcome, Why wrong (the reason word the editor opened the tag's note line with, or the audit's seeding), Your reasoning and Decided under there are the agent's copies of a decision an editor made on the claim, and Agent reading, Rule, Reading note and Read under are the agent's reading of it. No script writes an editor column, with one exception (hard rule 1): the decisions of the audit of 9 October are seeded once, marked with their source. On Claims `migrate-decisions` does it at setup, through a setup plan whose Challenged tags notes start with "From the audit of 9 October", which the plan check requires. On a new practice page `walkthrough.mjs start` creates the five decided claims, in a create under the demo's `runs/SETUP` marker. No agent or script ever acts as the editor (decisions P7 and P8; decision 93): the plan check refuses an editor column on every other update, production or practice page, and only people decide on Claims. The names come from `config.json` `editor_columns` (one list per table), which the plan check, the connector guard and the transcript checker all read.
- **Protected ids.** `config.json` lists the real tables and the old trial's tables under `protected_database_ids`, and three pages of the old trial (the hub "Editorial feedback loop", its tables page and its sandbox page) under `protected_page_ids`. Since the archive step both lists also hold everything archived (decision 84): the archive page, Structure proposal, Demos, Demo tests, every practice page made before 27 October with its tables and data sources, and the five tables of the first build with their data sources. `lib/config.mjs` refuses a config where a read-only source is not protected or one of the agent's own tables is; `pull.mjs` refuses to read a protected table as one of its own; the build never adopts a protected or archived table by its title (decision 85); `walkthrough.mjs start` refuses a parent that is the hub itself, one of the agent's own tables or a protected id, or that sits directly under a protected id or table; `run`, `where` and `verify` refuse a practice page that is in the archive (exit 2, "read only"), and `list` marks it "archived". This agent has no probe script (the previous build had one). The token can read the real claims table and the taxonomy (setup and the dry run needed that), so protection lives in code, and "reads only" is proved by counting the writes in a request log (`countRequests`): `pull --dry-run` and `setup verify` end with that count and fail if it is not 0, and `setup archive --plan-only` prints it.
- **The archive** (hard rule 8 as amended by P9). Only `setup.mjs archive`, in a builder session, moves anything, and only the eight objects `config.json` names: from the hub into the archive page, each one checked against the plan (`checkArchivePlan`: a known old id, the archive page as the destination, no protected target) and read back after the move. A block on the hub that is none of the eight is listed for a person and never touched. The REST client's `movePage` and `moveDatabase` are called from `lib/archive.mjs` and nowhere else; the connector guard still denies every move.
- **Geo** (hard rule 2). Geo is read only through `lib/geo-read.mjs`: two frozen queries (DebateTagged and ClaimDetails), with every id checked as 32 hex characters before it goes in; `send` refuses any document that does not start with `query` or that names a mutation or a subscription; it sends no Authorization header or other credential, follows no redirect, and reaches only the https hosts in `geo.allowed_hosts`. Its request log holds no bodies. `geo-pick.mjs` writes files only, never a table, and asks every time.
- **Content is data.** The judge's message quotes each claim, escaped so that it cannot close its own `<claim id>` element, and accepts only JSON of the schema's shape; the reading prompt, distill and the wording prompt quote rows the same way (the reading message escapes the claim, the agent's reason and the editor's note line, and its reply is checked against `schemas/reading-reply.schema.json`: every row key exactly once, one of the three readings, a rule the tag has, a note of at most 25 words). Claim text read from Geo is data in the same way. A reply decides nothing by itself: it is checked, then planned, then applied.
- **The connector guard.** `.claude/settings.json` runs `scripts/hooks/guard.mjs` before every Notion connector write. It always denies delete, move, duplicate and restore, any call that names a protected id, and any page write that names an editor column (every list of `editor_columns`) or sets Approved or Rejected. Everything else is denied unless `runs/SETUP` exists, and then only a plain page under a registered parent, content commands on a registered page (no deleting children) and schema calls on registered targets. It reads `config.json` and the markers itself and imports none of the agent's library modules. Rows are never written through the connector.
- **The builder session** is the marker `runs/SETUP` plus the registry in `runs/builder/`. Open one only for structural work and close it right after; the loop commands warn while it is open. A practice page's `start` keeps its own marker inside the demo folder while it seeds rows.
- **Drift and restore.** After every pull, the When to use, Description, Example Claims and Counterpart of each tag are compared with `rubric.lock`. A judged tag that differs stops the command (exit 4, naming tag and column). Put the text back, or run `restore.mjs --edition <edition in force> --confirm`; restore writes only When to use, so the other three columns are put back by hand.
- **Paused.** `runs/PAUSED` or Paused ticked in Agent settings stops every command that writes or judges; `pull` only reads and says so. There is no unpause command and no flag: a person clears it. Production's `runs/PAUSED` does not stop commands that run against a practice page (only `walkthrough start`); a practice page has its own file and its own Agent settings row.
- **Never delete or trash.** The settings deny the connector's delete, move, duplicate and restore tools; the REST client sends GET, POST and PATCH only and has no call or field that deletes, trashes or archives (a test reads its source to keep it so). Rows are superseded (a rule change becomes Rolled back); a practice page nobody needs is left where it is under Onboarding; it does no harm.
- **Secrets.** No key in the repo. `.env` is git-ignored and Claude Code's deny rules block reading it, `curl` and `git push`; the token stays inside `lib/notion-rest.mjs`, and request logs hold paths only. Geo takes no key.

## 7. The rulebook

`rubric/rubric.json` is the edition in force: each tag with its numbered rules (one `<n>.` line of When to use per rule), example claims, rule hashes and `judged`. A tag is judged only when its locked text holds rules, its capability is text (`config.json` `tags`) and it is in a judge group (`judge.groups`): today only Context-dependent. `rubric.lock` holds the edition, the rulebook hash, the time locked, the tag hashes, the locked When to use text and the other three compared columns. `history/<edition>.json` is the whole rulebook of each edition and is never rewritten. `CHANGELOG.md` gets one line per edition (date, edition, why). Editions are `YYYY-MM-DD.n`; a later change on the same day is `.2`. The fresh set under the hub starts the next edition with the same rules; its changelog line reads "setup: fresh tables under the hub (P9), copied from the taxonomy" (decision 88). Nothing is appended to a prompt: a rule changes only through an Approved lesson, a PASS and promote, and the version of `prompts/judge.md` is part of the cell-store key.

- **PASS** (promote). The candidate is the rulebook in force with that one rule replaced by the Editor wording, else the Proposed text. The example claims and the earlier decisions are judged under both rulebooks, and each flipped answer is read twice more per side. PASS needs every example claim right under the candidate, no earlier decision that was right now wrong, and every supporting row as the editor decided. Then, in this order:
  1. the Rulebook's When to use is written (with `expect`) and read back;
  2. the new edition is saved and committed (`rulebook edition <edition>: <title>`);
  3. a run of its own sets the rule change Live (`PASS: examples a/a, earlier b/b, yours c/c`) and updates Agent settings;
  4. the follow-up marks the supporting rows Fixed or Still wrong.

  If a stop falls after step 1, the rule is live and the same command finishes without another edition. On FAIL the rule change gets `FAIL: '<claim>' now <answer>` and the rulebook does not change; the distill model's sentence for Editor wording goes into the report and `card.md` only. A HOLD (nothing to check against) leaves the rulebook alone too.
- **Rollback.** The rule change must be Live and the rule must still read as that change left it. The lesson's Current text goes back into the Rulebook, a new edition "rolled back <title>" is saved and committed, and the rule change becomes Rolled back.
- **Restore.** `restore.mjs --edition <e> --confirm` writes the When to use of that edition over every tag whose text differs and saves a new edition "restored from <e>" (committed). It is the answer to a drift stop and the way back to any older edition.
- **Adoption.** A tag without rules in force whose row was edited in Notion is not a drift: the next writing command saves a new edition "adopted from Notion: <tag> <columns>" and goes on (`status` only warns). If the new text holds numbered rules the tag is judged from that edition, but only once an engineer lists it in `judge.groups`. Adoption writes the files but does not commit; the next committed edition carries them.
- Commits run `git add agents/claim-tagger-mvp/rubric` and then `git commit -m`, which takes anything else that is staged: keep the index clean before a promote, rollback or restore. Practice pages are never committed. Nothing pushes.

## 9. Tests

`node --test tests/mvp/` runs this agent's suite; `npm test` is `node --test tests/` and adds the previous build's. They are built to run without the network, a real Claude, a real token or a real Geo. Scripts take `--driver fake` or the `driver: 'fake'` option. The fakes are in `tests/mvp/fixtures/`:

- `fake-notion.mjs`: an in-memory Notion behind `fetchImpl`. It checks the token and Notion-Version, logs every request, `failNext` fails the next matching ones, `editRow` plays an editor (relations take page ids), views can be made, listed, renamed and changed (filter, sorts, configuration), a column can be added or renamed, and ids can be protected. `fake-notion-pages.mjs` adds child pages, tables and linked views for the practice-page builder, and the moves, title updates and block positions of the archive step.
- `fake-geo.mjs`: a fake Geo GraphQL server for `lib/geo-read.mjs` and the pick: quotas, a short space, the month spread, audit forcing and left-outs, duplicates, determinism, retries and page halving, the refusal of anything but a query, and the refusal to overwrite a pick.
- `fake-claude.mjs`: stands in for `claude -p`; `FAKE_CLAUDE_MODE` is ok, invalid-once, invalid-always, transient-once, transient-always, usage-window or wrong-model. `fake-claude-loop.mjs` adds answers that depend on the rule text, for promote and the loop. A prompt headed `# Reading` gets one reading per row of the message: the entry of the `FAKE_CLAUDE_READINGS` file for that row key, else Rule unclear on the rule the agent's reason cites; `FAKE_CLAUDE_ONLY` (reading, distill, wording, judge) limits the failing modes to those calls; `fake-claude-loop.mjs` passes reading calls through. `helpers/loop-world.mjs` has `w.readings(table)` and a `w.review(...)` that needs no Why wrong.
- `transcripts/`: headless runs for the transcript checker. `tests/mvp/helpers/` builds throw-away worlds (`loop-world`, `promote-scenario`, `setup-world`, `tables`).

The walkthrough's main check is the seven-step test on the fakes (`tests/mvp/walkthrough.test.mjs`), where the fake Notion's own rows play the editor at steps 3 and 5 (decision 93).
