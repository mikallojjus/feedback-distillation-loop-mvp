# claim-tagger-mvp: the claim tagger and its editor feedback loop

Read this first. It is the one runbook of this agent, written for the engineer; editors use the skill `/claim-tagger` and never need it. The repository's `CLAUDE.md` holds the hard rules, `docs/mvp-2026-11/STRUCTURE-V2.md` and `setup/structure.json` the Notion layout of the page "Claim tagger v2" (decisions P42 to P49), `docs/mvp-2026-11/PORT-V2.md` the port of the loop to it, `docs/mvp-2026-11/OVERNIGHT.md` the night of 30 to 31 October that made it the default, `docs/mvp-2026-11/CONTRACTS.md` the file shapes (not yet rewritten for v2 in every section) and `docs/mvp-2026-11/WORKLOG.md` the build log. The per-claim version, where editors decided a whole claim on the first page "Claim tagger" (`HUB-AND-GEO-CLAIMS.md`; `STRUCTURE.md` is the approved proposal of 15 October), is the git tag `claim-tagger-v1`; this file describes it only as history. The previous build in `agents/claim-tagger/` is read-only history, but this agent still imports eight small modules from its `scripts/lib/` (exit-codes, hash, jsonl, notion-values, pyjson, rng, stats, validate): that folder stays and is not edited.

## 1. What the agent is, and where it lives in Notion

The agent reads Geo claims from the Notion table Claims, asks a pinned Claude model which tags of the rulebook apply to each claim (in this build only Context-dependent has rules), and writes its answer on Tag decisions, one row per claim and tag it judged: Agent proposal (Applies, Does not apply or Can't tell), Agent confidence, Agent reason, Agent status and Rulebook edition. Editors decide on those rows (decisions P42, P45 and P46): they tick Agent is right (the agent's answer is the decision) or set Tag outcome (Applies or Does not apply), and may write Your note in plain words. They never name a reason or a rule. Tag outcome wins when both are set; a tick on a Can't tell row decides nothing, and the row keeps waiting. The agent never writes those three columns. It records the first sight of a decision in Decided under: the edition the proposal was made under, and for a tick also what it agreed with (`<edition> · agreed <Outcome>`), so that a later tag run, which moves the proposal of a decided row too, cannot change what was agreed. On Claims it writes a summary of each claim in eight columns of its own (Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Agent's view of your decision); Claims has no editor column and is read only for editors. Where a decision differs from the proposal, the agent reads the disagreement itself (Agent's view of your decision: Agent slip, Rule unclear or Rule should change; the Rule it points at; one line in Why the agent thinks so), turns the readings that point at a rule into proposed rule changes, tests an approved change with a safety check, and only after a PASS writes the new rule into the Rulebook and saves a new edition of the rulebook. Nothing is ever appended to a prompt: the rulebook text is the only thing that learns, and it learns only from decisions people made (decision P8).

Claims holds the claims copied from the first page on 30 October (P47): the 200 Geo claims tagged Debate of the pick of 27 October (decision P6), the 400 Claude chose in the import of 29 October (P38 to P41), and from now on the claims editors add with `/claim-tagger add` (P35 to P37, below). A new tag starts with nothing decided: a claim decided on Context-dependent has no decision on another tag until someone makes one. Every decision on Tag decisions is training data.

Needs: Node 22 or later, the `claude` CLI on the subscription (no API key), `NOTION_TOKEN` in `.env` (git-ignored; never opened, printed or sent anywhere), and the Notion integration connected to the hub page. Geo needs no key: it is read with queries only, through `scripts/lib/geo-read.mjs`.

Everything sits under the Notion page "Claim tagger v2", the hub (`408273e214eb81d78f78ecfe4885d1ab`), a sub-page of the first page "Claim tagger" (`3fa273e214eb805199f3d12ef01db453`, `notion.root_parent_page_id`). It was built empty on 29 October as "Claim tagger v2 (in preparation)" (checkpoint 1, P44) and retitled for the team introduction of 31 October (P49). Its body holds one line, "Decide each claim and tag in Tag decisions: tick Agent is right or set Tag outcome. The first page, "Claim tagger", is kept for reference.", then the links to Your queue, Needs your note, Agent disagreed and Lessons waiting, each with a line under it that says what to do there (P45), then the five tables, each a full-page table with a line of description under its name. It has no sub-page: no Onboarding and no archive. The ids are in `config.json` (`"profile": "v2"`).

The three editor views list rows (a claim and one tag), sorted by Claim A to Z, then Agent confidence lowest first, so that a claim's rows stand together; no view shows Agent confidence, and cells wrap. Your queue lists the rows whose Agent status is Waits for you and whose Tag outcome is empty, and that are not ticked unless the proposal is Can't tell; it shows Claim, Open claim, Tag, Agent proposal, Agent reason, Agent is right, Tag outcome and Your note, the three editor columns at the right end. A row leaves it the moment it is decided, and keeps Waits for you in Agent status until the next tag run. Needs your note lists the rows whose Why the agent thinks so contains "without your note" (a disagreement the agent read with no note; the view lists a row only once distill has read it, while `status` counts it at once) and shows Claim, Tag, Agent proposal, Tag outcome, Agent's view of your decision, Why the agent thinks so and Your note. Agent disagreed lists the rows whose Agent status is Disagrees with your decision and shows Claim, Tag, Agent is right, Tag outcome, Agent proposal, Agent reason, Your note and Rulebook edition. Lessons waiting lists the rule changes that are Proposed or Approved, with Editor wording beside the texts. Each table's own view stays the first tab (`default_view` in `setup/structure.json`): Claims calls it "All claims" (Geo Name, Geo Space, Agent status, Agent tags, Tags waiting, Tag decisions, Agent reasons, Agent's view of your decision, Geo URL); the Rulebook's is "Rulebook" (Name, Category, Status, When to use, Example Claims); Tag decisions shows Claim, Tag, Agent proposal, Agent status, Agent is right, Tag outcome, Your note, Agent's view of your decision and After the rule change. Open claim, on a row, and Tag decisions, on the claim, are the two sides of one two-way relation: the agent writes Open claim and Notion fills the other side. Reports link the views through `config.json` `notion.views`; the table's own link is the fallback.

The first page "Claim tagger" keeps its own five tables as they were on 30 October, its Onboarding page with the practice pages, and its archive "Feedback Distillation MVP (archive, to 27 Oct 2026)", which holds the first build of 15 to 22 October. All of it is protected and read at most (section 6): `copy-live.mjs` reads the first page's tables, and nothing writes them. Read only and protected besides: the taxonomy "Claim Tags — verified" and the real "U.S. Politics debate claims". The old hub and sandbox under "Editorial feedback loop" are history.

## 2. Commands

Run from the repository root. `.claude/settings.json` lets Claude Code run the scripts below without asking, except `setup.mjs`, `geo-pick.mjs`, `rollback.mjs` and `restore.mjs` (it asks every time); `copy-live.mjs`, `headless-check.mjs` and `transcript-check.mjs` have no rule, so it asks for those too. The loop scripts also take `--pull <pull-id>` (use that pull instead of pulling again), `--run-id <id>` and `--help`; `--driver fake` is for tests.

The loop, and what each step writes in Notion:

| Step | Who | Writes in Notion |
|---|---|---|
| Add | editor types `add <Geo links or IDs>` | Claims: new rows with the nine Geo columns only (Geo Name, Geo ID, Geo URL, Geo Space, Geo Created, Geo Sources with its links, Geo Is factual, Geo Tags, Geo Topics), read from Geo, each read back. It never changes an existing row and writes no other table and no agent column; the new claims are not tagged and have no rows in Tag decisions yet |
| Tag | editor types `tag` | Tag decisions: a row for every judged claim and tag that has none (Claim, Open claim, Key, Tag), and on every row it judged, decided or not, Agent proposal, Agent confidence, Agent reason and Rulebook edition where they differ, Agent status (Waits for you on Can't tell, Disagrees with your decision where a decided row's new answer differs from the decision, Could not read, else Done) and Decided under for a decision it finds for the first time. Claims: the summary, Agent tags (the decided Applies rows and the undecided Applies proposals), Agent confidence (the lowest of the claim's rows), Agent reasons (one line per judged tag), Agent status (Waits for you, else Disagrees with your decision, else Could not read, else Done), Tags waiting (the undecided Can't tell rows), Agent edition, Agent remarks (never Agent's view of your decision). Agent settings: edition, Last run summary |
| Decide | a person, in Your queue or anywhere in Tag decisions; or an editor's Claude, when the editor types `decide` | Agent is right, Tag outcome, Your note (Tag decisions). No script of the loop writes these. A person sets them in Notion; Claude writes them through the Notion connector between `decide.mjs open` and `decide.mjs check`, after the editor's OK on a draft, on the rows the open run lists, only the fields the decision gives, and nothing else (decisions P18 to P25, 113 to 120, moved to Tag decisions by P47). A note is plain words, with no reason word and no rule (P45) |
| Distill | editor types `distill` | First it reads the decisions: Tag decisions gets Decided under on a decision made since the last tag step and, on every disagreement (a decided row whose outcome differs from the proposal, not marked Fixed), the reading: Agent's view of your decision, Rule, Why the agent thinks so, Read under; Claims: Agent's view of your decision (one line per read tag). Then it drafts: Rule changes, one row per lesson from the readings that point at a rule, Status Proposed. Agent settings: Last run summary |
| Approve | the rule owner, a person, in Lessons waiting | Status Approved or Rejected, Editor wording (the agent never writes these) |
| Promote | editor types `promote` | PASS: Rulebook (When to use), Rule changes (Live, result), Agent settings, and a new committed edition in `rubric/`. FAIL or HOLD: only the result and Agent settings |
| Follow-up | by itself after a PASS | Tag decisions: After the rule change (Fixed or Still wrong) and Agent status (Done or Disagrees with your decision) on the rows the change rests on; their proposal columns wait for the next tag run. Claims: the summary columns of those claims (Agent confidence only where every judged tag was checked again) |

**The add step** (decisions P35 to P39, `docs/mvp-2026-11/ADD-CLAIMS.md`, `CONTRACTS.md` section 20). An editor can bring specific Geo claims into Claims by Geo link or Geo ID (`https://www.geobrowser.io/space/<space>/<claim>`, or the 32-character ID), any number in one command (P38 lifted the cap of 50), or from a selection file with `--claims-file` (`schemas/import-selection.schema.json`, the file the import writes; validated, every Geo ID once, before anything is read). `add.mjs` pulls the tables, runs the usual checks (paused: exit 3; drift: exit 4; the columns the scripts need), reports a Geo ID that Claims holds as already there, reads the others from Geo through `lib/geo-read.mjs` (queries only; the log is `runs/<run-id>/geo-requests.jsonl`, and a request that is not a query stops the run with exit 2), and refuses a claim that Geo does not hold, that is not of the Claim type, that is in none of the allowed spaces (`geo.allowed_spaces`: the canonical spaces except Podcasts, P39; `geo.spaces` keeps the six seed quotas for the pick), that has no name, or whose text (`normaliseName`, the pick's comparison) is the same as a claim in Claims or an earlier claim of the same command (the existing claim is named). The row is built by `lib/geo-row.mjs`, the builder `geo-pick.mjs` uses too: the nine Geo columns, Geo Space is the allowed space's name, and Notion makes a missing option on write (`setup.mjs verify` accepts the listed Geo Space options that are not live yet); Geo Tags only with option names the column already has (the others are left out and listed in run.json; no Geo Tags option and no column is made), a source link at a protected id refuses the claim, the links of Geo Sources go in beside the text (`withLinkedSources`). Right before the plan is made Claims is asked again for those Geo IDs, so a claim another editor added in the meantime is dropped as already there; that narrows the window in which two editors adding the same claim at the same moment could make a repeated key (which stops every loop script), it does not close it. So after the read-back Claims is asked once more for the Geo IDs the run created: one that now has two rows is reported by the run that made it (exit 2, the claim named, both page ids and the one to remove in run.json `add.in_claims_twice`; the one to remove is the one the pull treats as the extra one, in the pull's order), and the engineer removes that row by hand. The plan has the script name `add`, and `lib/plan.mjs` gives that name one narrow allowance: it may only CREATE claims rows with the key and the nine Geo columns (never an update, another table, an agent column or an editor column); no other script may create a claims row but setup. It is applied with the ledger and every row is read back. The new rows are not marked and not tagged: `/claim-tagger tag` reads them (`status` counts them as not read yet). Exit 0 when at least one claim was added; exit 2 when none was (everything already there, every item refused, more than 50 items); exit 1 when Geo or Notion could not be read or a write did not finish (the editor types the command again with the same links: it pulls first, so a row that landed is already there; a stop part way says how many claims were added and read back before it stopped, and how many more may have been: rows written but not read back and creates that answered an error, in run.json `written_unchecked` and `maybe_written`; `not_written` is only for rows with no page). run.json has `add` (the items, the claims added with their page ids, the claims not written after a stop, the reasons for the others with the existing claim of a same-text refusal, the Geo Tags left out) and `geo_requests`. `setup.mjs verify` counts Claims rows whose key is a Geo ID (32 hex characters) that is not in the pick as "added after setup" and no longer calls them a difference; any other row that is not in the pick is still an extra row, and the Geo columns of an added row are not checked.

**The import** (decisions P38 to P41, `.claude/skills/claim-tagger/references/import.md`, evidence `docs/mvp-2026-11/evidence/32-import-400/`). `/claim-tagger import [count]` has Claude choose a batch of Geo claims (400 by default):
- Debate-tagged, Claim-typed claims with a name in the allowed spaces;
- not by the Geo bot (`geo.bot_spaces`; a claim's author is the `createdById` of the edit whose version key is the smallest `validFromKey` of its Name values);
- not in Claims by Geo ID or text;
- spread over the spaces (the seed's weights) and months;
- about 70% likely to break the rulebook, the rest near-misses and controls.

Claude reads Geo only with `geo-query.mjs`, scores a seeded month-spread sample with subagents against criteria it writes from the Rulebook (for choosing only, never in `rubric/` or the judge prompt), writes a selection file, shows the owner a summary, and on a yes runs `add.mjs --claims-file`. No script decides a claim and nothing is tagged until someone asks.

**The decide step** (decisions P18 to P25 and 113 to 120, moved to Tag decisions by P47; `docs/mvp-2026-11/CLAUDE-DECIDES.md` describes the per-claim form, `PORT-V2.md` section 2.16 the per-row one). An editor can tell Claude to decide rows, in a conversation (P21): in their own words on claims or rows they name or describe, by asking Claude to judge ("decide the first 6"), or by asking for the notes of rows they already decided by hand. Claude drafts the decisions (a table, one line per row: the claim and the tag, the agent's proposal, the decision, which is the tick or a Tag outcome, the note after word for word, and "changes an earlier decision" for a row that held one), the editor iterates, and nothing is written before the editor's OK; the OK is the approval of the writes (P23), and the guard hook is the gate: `.claude/settings.json` has no permission rule for the connector's `notion-update-page`, so the hook's "allow" lets a decision through without a prompt, and a hook that cannot run leaves the normal prompt.
- `decide.mjs list` (read only, for Claude; it reads the newest pull on disk) prints the rules in force and the rows: each with its claim between `<claim>` tags, the tag, the agent's proposal, confidence, reason and view, what the row holds in the three editor columns, and `seen`, a fingerprint (12 hex digits) of the row's page id, tick, Tag outcome, note and Agent proposal (a tick agrees with the proposal as shown), so that it belongs to that row only. Which rows: the rows of Your queue in the view's order, claim A to Z then the lowest confidence first (no flag); every row of the named claims and the one row a Key names (`--claims <Geo IDs or Keys>`); or every row of the table in compact blocks (`--all`). The rows of one claim come together under one claim line.
- `decide.mjs open --decisions '<json>'` takes, for each row, `row` (the Key or the page id), `seen`, and `agent_is_right` (only `true`), `outcome` (Applies or Does not apply), `note`, or some of them (a missing field stays as it is, P24; any row, decided or not, P22). It pulls the tables itself and checks the decisions: every row is in that pull and still has the fingerprint `seen`, otherwise "changed in Notion since Claude read it"; no row is named twice; a decision gives a tick, an outcome or a note; the tick and the outcome are not given together; a tick on a row whose proposal is Can't tell is refused ("decides nothing; give an outcome"), and so is a tick on a row that has a Tag outcome (the outcome would win over it); the agent is not paused; no other run is open. It records the fields given, what each row held before, `seen` and `had_decision` in the run folder (`decisions.json`), writes the marker `runs/DECIDING` (`run_id`, `opened_at`, `page_ids`, `root`; a regular file) and prints, above each connector call, a line that says what it changes (`<Key>: the agent is right (Applies)`, `<Key>: outcome none → Does not apply; note added`, with "changes an earlier decision" when the row held one), then the exact input: `update_properties` with only the properties given, the tick as `"Agent is right": "__YES__"` (the connector's form for a ticked box).
- The guard hook lets a `notion-update-page` with `update_properties` through only for some of the three Tag decisions columns, with those values (Agent is right `"__YES__"`, Tag outcome Applies or Does not apply, Your note a string), on a page that a marker younger than two hours lists in this folder, and not while `runs/PAUSED` exists.
- `decide.mjs check` pulls Tag decisions again, compares each row with the record (the tick when one was given, Tag outcome when given, the note as trimmed text when given), removes the marker whatever happens and prints the report: exit 0 and "N rows decided and read back" with how many differ from the agent (a tick, or an outcome equal to the proposal, is the same; a note given alone on a row that holds no decision is "Not compared with the agent") and, when some rows held a decision before and the decision changes their outcome or note, "Changed an earlier decision"; or exit 1 and the rows that did not read back (a row whose given fields still hold what they held before is "not written"; the Next line is "type /claim-tagger decide again and name …", with "; … is no longer in the Tag decisions table" for a row that is gone, and sends the editor to Tag decisions only when every row that differs is gone). Every path after `open` ends in `check`, also when a write was refused. If Notion cannot be read, `check` says that the decisions were sent and not read back; `/claim-tagger decide check` (`decide.mjs check` with no marker) then reads the newest decide run back from its record, and reads while the agent is paused. A decide run opened and never checked goes stale after two hours; the next `open` names it, and `decide.mjs check --run <id>` reads it back.
- `transcript-check.mjs` and `headless-check.mjs` accept these connector writes in the transcript of `/claim-tagger decide` only. Decide runs on the agent folder only.

**What distill does first: it reads the decisions** (decisions 64 to 73 and P45; `PORT-V2.md` sections 1.8 and 2.14). Distill first records Decided under on every row that holds a decision and has no record yet, in the same plan as the rest. A decision is a row with a Tag outcome, or a tick on a row whose proposal is Applies or Does not apply (`rowDecision` in `lib/decisions.mjs`, the one reader of the three editor columns). An agreement has nothing to read. A row marked Fixed in After the rule change is never read again. A row whose Read under (`<edition> · <hash8>`: the hash over the outcome, the proposal, the note and the edition the proposal was made under) is current keeps its reading and costs nothing. Every other disagreement goes to the model (`models.distill` at `distill.reading_effort`, medium; `prompts/reading.md`) in batches of `distill.reading_batch` (10), two attempts per batch, each refused reply kept as `rejected/reading-batch-<n>-attempt-<k>.md`; a batch that fails twice leaves its rows unread this run and the next run tries again. No word of a note is taken as the answer (P45): a note that names a reason ("Agent slip") is evidence of what the editor saw, and the model reads the rules itself; the per-claim version's verbatim path is gone. A disagreement with no note at all is still read, and flagged in code, never by the model: its Why the agent thinks so opens with "without your note" and the claim's line carries ", without your note", which is what Needs your note filters on. A promote alone makes no reading stale (decision 66 as amended on 22 October); a tag run or the follow-up that proposes again under the new edition does. The lessons are then drafted from the rows read Rule unclear or Rule should change, grouped by tag and the reading's rule (else the rule the agent cited), Fixed rows left out, at least `distill.min_claims` claims per group; Agent slip rows draft nothing and may be counter-evidence; a reading of a decision without a note (decision 78) is the agent's guess: it drafts nothing and is no counter-evidence either until the editor writes a note; the lesson's Kind is derived (Change the rule when any row of the group reads Rule should change, else Clarify wording). The report: "Distill: read N of your decisions and drafted one rule change from M of them." (M is the number of decisions the rule change rests on; or "Distill: read N of your decisions; no rule change to draft; <why>.", with "; M could not be read this time" when a batch failed, and "; K of your decisions have no note and wait in Needs your note" while some decision has none), a table of Read, Point at a rule (readings that blame the rule and rest on a note), Agent slips, Without a note and Rule change (the counts of this run), and a Next line: reject a rule change that rests on a decision the agent now reads as its own slip (decision 79: "the rule change "<title>" rests on a decision the agent now reads as its own slip" in the sentence, nothing new drafted for that rule meanwhile, promote holds with exit 10, the follow-up marks only rows that still point at a rule, and only the editor sets Rejected); else Lessons waiting when a lesson was drafted; else approve or reject (a rule change is Proposed) or promote (Approved); else Needs your note when a disagreement has no note ("add a note on N rows in Needs your note"); else status. Distill exits 2 only when something was to read, nothing could be read and no rule change was drafted (or every reply of a lesson group was unusable).

**The status row "Your decisions"** (decision 74; counted in rows on v2). Three counts of rows, made from Tag decisions the way distill brings it up to date, over decided rows that differ from the proposal and are not Fixed: `<n> to read` (a row never read or stale), `<n> points at a rule` (`<n> point at a rule` from two: a current reading of Rule unclear or Rule should change with a note of the editor's, decision 78; Still wrong stays open) and `<n> without a note`. The row sits between Your queue and Lessons waiting, shows the parts that are not zero ("3 to read, 1 without a note") and is left out when all three are zero. `status --json` holds them as `queue.to_read`, `queue.pending_rule_decisions` and `queue.needs_note`, and the claims the agent has not read yet (Agent status empty on the claim) as `queue.unread`. The Next line is the first that applies: start at the top of Your queue, or decide the rows there ("decide your nine rows in Your queue"); claims the agent has not read yet ("Next: type /claim-tagger tag to read N new claims."); distill, while something is to read or at least `distill.min_claims` decisions point at a rule, and no rule change is Proposed or Approved; reject a recanted rule change (the Lessons waiting row then says "1 rule change to reject (rests on a decision the agent now reads as a slip)"); approve or reject; promote; tag. With nothing in Your queue and no rule change the sentence follows the row: "nothing is paused; the agent has N of your decisions to read." or "...; N of your decisions have no note."; when nothing else is to say, it is "nothing is paused; the agent has N new claims to read." The row Your queue counts exactly what the view lists (`countYourQueue`: "<n> rows, lowest confidence first", else "nothing waits"), and ends with the claims the agent has not read yet ("nothing waits; N new claims not read yet"); a row leaves the view the moment it is decided, so a decided row the agent has not read yet is told in the row Your decisions ("<n> to read"), never in Your queue (`queue.decided_listed` in `--json` counts the decided rows whose Agent status still says Waits for you).

The skill relays the report verbatim first. When the report's Next line sends the editor to Notion (after `tag`, `distill`, a `promote` that ended in FAIL, a `follow-up` that left rows in Agent disagreed, and `status` when it says to decide or approve), it adds one checklist of at most five lines below the report: which view to open, which columns to fill in and in which order, what to look at, and the next command to type. The checklists are in `.claude/skills/claim-tagger/references/guide.md`, in the words of the page "Claim tagger v2" (same column and view names). The report itself stays three parts.

## 5. Models and runs

| Work | Model | Effort | Prompt |
|---|---|---|---|
| Judge: every claim, the safety check's two rulebooks, the follow-up | `claude-sonnet-5-5` | medium | `prompts/judge.md` |
| Distill, first: the reading of each disagreement (batches of 10 rows; every disagreement, P45) | `claude-opus-5-5` | medium | `prompts/reading.md` |
| Distill: lessons from the readings that point at a rule | `claude-opus-5-5` | high | `prompts/distill.md` |
| Wording sentence after a FAIL (30 words at most, with its reason in 40; report and `card.md` only, never Notion) | `claude-opus-5-5` | high | `prompts/wording.md` |

Every call is `claude -p` through `lib/claude.mjs`: no shell, the prompt on standard input, each claim quoted as data in a `<claim>` block, no tools, one turn. The pinned model must appear in the answer's model usage, else exit 4 and the answer is dropped. `--bare` and `--fallback-model` are refused in code. The previous build's fallback subagents were removed; no script of this agent calls a subagent.

**Adaptive runs.** Run 1 reads every claim once, in batches of `judge.batch_size`, `judge.concurrency` batches at a time. A cell (one claim, one tag) is unsure when the decision is `ask_editor` or its probability lies strictly between 0.25 and 0.75. Claims with an unsure cell are read again (run 2), at most 30% of the run's claims, least sure first; the rest are listed as `capped` in `run.json`. Run 3 happens only where runs 1 and 2 disagree. Answers already in the cell store are never asked again, so a repeat run asks nothing. `propose` then takes the majority of the reads (`ask_editor` wins a tie); a cell is unsure when a read failed, the reads disagree or the mean probability is inside the band, and each unsure cell without a row becomes a queue row.

**Error classes.** An invalid reply (not JSON, a claim or tag missing, a break of `schemas/judge-reply.schema.json`) gets one more attempt for its batch; after that the batch's claims are stored as errors, the next run tries them again, and this run ends with exit 2; each refused reply is kept as it came under the run's `rejected/` folder, with the problems listed, so that a batch that fails twice can be read. A transient error (429, overloaded, busy, timeout, any other failed call) waits `judge.transient.backoff_ms` and retries; the third in a row stops the run with exit 1 and its resume command. Only the CLI's usage-window wording stops a run with exit 75, nothing written for that batch; the window is checked first, so a 429 that says the limit was reached counts as the window.

| Exit | Meaning |
|---|---|
| 0 | ok |
| 1 | stopped: run the same command again (three transient errors in a row, a write that did not finish, Geo could not be read, an unexpected error) |
| 2 | invalid: usage, no token, a refused plan, a duplicate key, a read-back that differs, a batch that could not be read (distill: only when rows were to be read, none could be, and no rule change was drafted), a claims table without the agent's reading columns, a decide input that does not fit (a tick on Can't tell, a tick and an outcome together), a per-claim step of setup on v2, the parked walkthrough |
| 3 | paused |
| 4 | drift (the rulebook text in Notion or the file on disk no longer matches the saved edition) or another model answered |
| 5 | not used by this agent; the shared table calls it trust breaker |
| 10 | HOLD: nothing to check a change against |
| 11 | FAIL: the safety check failed; the rulebook did not change |
| 75 | usage window (editors read "your Claude allowance ran out"): resume later |

## 6. Safety

The ten hard rules in `CLAUDE.md` apply; this is how they are kept here.

- **Plan before write.** A script that writes builds `plan.jsonl` first; nothing is sent before the plan is checked, and `--plan-only` stops there.
  - `checkPlan` (`lib/plan.mjs`) refuses the whole plan for: a table that is not one of the five in `config.json`; a column outside the table's allowlist; an editor column (below); a Status on a rule change other than Proposed, Live or Rolled back; a protected id in any string; a missing or repeated key.
  - `applyPlan` sends the ops in order through `lib/notion-rest.mjs` (paced at `requests_per_second`, with retries). It never moves anything: the client's two moves belong to the archive step alone, and the client has no call that deletes or trashes. It skips an update whose `expect` no longer matches the pulled value, appends one ledger line per op and reads every written page back.
  - Success is claimed only after the read-back: a difference is exit 2, a write that could not be read back is exit 1, and the next run re-reads, never re-writes.
- **Allowlist per table.** Tag decisions: Claim, Open claim, Key, Tag, Agent proposal, Agent confidence, Agent reason, Agent status, Rulebook edition, Decided under, the agent's reading (Agent's view of your decision, Rule, Why the agent thinks so, Read under) and After the rule change; never Agent is right, Tag outcome or Your note. Rule changes: Lesson, Tag, Rule, Kind, Current text, Proposed text, Safety check result, Supporting rows, Status. Agent settings: Rulebook edition, Last run summary. Rulebook: When to use. Claims: Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Agent's view of your decision. Only distill writes the reading columns; propose and the follow-up never write or clear them. A create at setup may fill every column of the table it seeds; a plan of `add` may only create Claims rows with the key and the Geo columns, and a plan of `copy-live` has its own list, on a v2 config only (section 3). The check is on columns, not rows.
- **Editor columns** are Agent is right, Tag outcome and Your note (Tag decisions), Editor wording and the Status values Approved and Rejected (Rule changes), Paused (Agent settings); Claims has none (`editor_columns.claims` is empty). The plan check refuses an editor column in every plan of the loop. The one script that writes some is the copy (`copy-live.mjs`, P47): Tag outcome and Your note from the decisions made on the first page (and Editor wording, Status and Paused as they are there), keeping a value a person set on v2 unless it is told to overwrite it; it never sets Agent is right. An editor's Claude may write the three Tag decisions columns through the connector when the editor asked it to decide rows (the decide step, decisions P18 to P20): not a script, not a plan, and only on the pages an open `decide.mjs open` run lists. No script ever acts as the editor (decision 93), and no agent decides a row unless an editor asked for it. The names come from `config.json` `editor_columns` (one list per table), which the plan check, the connector guard and the transcript checker all read.
- **Protected ids.** `config.json` lists the real tables and the old trial's tables under `protected_database_ids`, and the old trial's pages under `protected_page_ids`. Both lists also hold everything archived on 27 October (decision 84: the archive page, Structure proposal, Demos, Demo tests, every practice page made before 27 October with its tables and data sources, and the five tables of the first build) and, since P48, the first page's own five tables with their data sources and views, its Onboarding page with the practice pages, and its archive page. `lib/config.mjs` refuses a config where a read-only source is not protected or one of the agent's own tables is; `pull.mjs` refuses to read a protected table as one of its own; the build never adopts a protected or archived table by its title (decision 85); the copy stops when a target id is also one of its sources. This agent has no probe script (the previous build had one). The token can read the real claims table, the taxonomy and the first page (setup, the dry run and the copy needed that), so protection lives in code, and "reads only" is proved by counting the writes in a request log (`countRequests`): `pull --dry-run` and `setup verify` end with that count and fail if it is not 0.
- **The archive** (hard rule 8 as amended by P9) was done once, on 27 October, for the first page: only `setup.mjs archive`, in a builder session, moved the eight objects `config.json` named into the archive page, each checked against the plan and read back. On v2 the step refuses. The REST client's `movePage` and `moveDatabase` are called from `lib/archive.mjs` and nowhere else; the connector guard still denies every move.
- **Geo** (hard rule 2). Geo is read only through `lib/geo-read.mjs`: two frozen queries for the scripts (DebateTagged and ClaimDetails), plus `scripts/geo-query.mjs` for Claude's own read-only queries in the import (P38; one document per call, logged to `runs/geo-query/<run-id>/requests.jsonl` and counted back), with every id checked as 32 hex characters before it goes in; `send` refuses any document that does not start with `query` or that names a mutation or a subscription; it sends no Authorization header or other credential, follows no redirect, and reaches only the https hosts in `geo.allowed_hosts`. Its request log holds no bodies. `geo-pick.mjs` writes files only, never a table, and asks every time.
- **Content is data.** The judge's message quotes each claim, escaped so that it cannot close its own `<claim id>` element, and accepts only JSON of the schema's shape; the reading prompt, distill and the wording prompt quote rows the same way (the reading message escapes the claim, the agent's reason and the editor's note line, and its reply is checked against `schemas/reading-reply.schema.json`: every row key exactly once, one of the three readings, a rule the tag has, a note of at most 25 words). Claim text read from Geo is data in the same way. A reply decides nothing by itself: it is checked, then planned, then applied.
- **The connector guard.** `.claude/settings.json` runs `scripts/hooks/guard.mjs` before every Notion connector write. It always denies delete, move, duplicate and restore, any call that names a protected id, and any page write that names an editor column (every list of `editor_columns`) or sets Approved or Rejected, except the decide step: a `notion-update-page` with `update_properties`, only some of the three Tag decisions columns, with the values `decide.mjs open` prints (Agent is right `"__YES__"`, Tag outcome Applies or Does not apply, Your note a string), on a page that a live `runs/DECIDING` in this folder lists (decision 114; the protected-id check comes first). That is the one "allow" the guard gives. Everything else is denied unless `runs/SETUP` exists, and then only a plain page under a registered parent, content commands on a registered page (no deleting children) and schema calls on registered targets, each answered "ask" so that the editor of the builder session still sees a prompt. The guard is the gate of the decide step: `.claude/settings.json` has no permission rule (neither "allow" nor "ask") for `notion-update-page`, so a guard that cannot run leaves the normal permission prompt instead of letting every update-page through. It reads `config.json` and the markers itself and imports none of the agent's library modules. Rows are never written through the connector, except the decide step's three columns.
- **The builder session** is the marker `runs/SETUP` plus the registry in `runs/builder/`. Open one only for structural work and close it right after; the loop commands warn while it is open.
- **Drift and restore.** After every pull, the When to use, Description, Example Claims and Counterpart of each tag are compared with `rubric.lock`. A judged tag that differs stops the command (exit 4, naming tag and column). Put the text back, or run `restore.mjs --edition <edition in force> --confirm`; restore writes only When to use, so the other three columns are put back by hand.
- **Paused.** `runs/PAUSED` or Paused ticked in Agent settings stops every command that writes or judges (the copy too); `pull` only reads and says so. There is no unpause command and no flag: a person clears it.
- **Never delete or trash.** The settings deny the connector's delete, move, duplicate and restore tools; the REST client sends GET, POST and PATCH only and has no call or field that deletes, trashes or archives (a test reads its source to keep it so). Rows are superseded (a rule change becomes Rolled back); the copy leaves alone the v2 rows the first page does not have.
- **Secrets.** No key in the repo. `.env` is git-ignored and Claude Code's deny rules block reading it, `curl` and `git push`; the token stays inside `lib/notion-rest.mjs`, and request logs hold paths only. Geo takes no key.

## 7. The rulebook

`rubric/rubric.json` is the edition in force: each tag with its numbered rules (one `<n>.` line of When to use per rule), example claims, rule hashes and `judged`. A tag is judged only when its locked text holds rules, its capability is text (`config.json` `tags`) and it is in a judge group (`judge.groups`): today only Context-dependent. `rubric.lock` holds the edition, the rulebook hash, the time locked, the tag hashes, the locked When to use text and the other three compared columns. `history/<edition>.json` is the whole rulebook of each edition and is never rewritten. `CHANGELOG.md` gets one line per edition (date, edition, why). Editions are `YYYY-MM-DD.n`; a later change on the same day is `.2`. The fresh set under the hub starts the next edition with the same rules; its changelog line reads "setup: fresh tables under the hub (P9), copied from the taxonomy" (decision 88). The v2 page started the edition 2026-10-30.1 the same way, with the v2 Rulebook page ids (section 3). Nothing is appended to a prompt: a rule changes only through an Approved lesson, a PASS and promote, and the version of `prompts/judge.md` is part of the cell-store key.

- **PASS** (promote). The candidate is the rulebook in force with that one rule replaced by the Editor wording, else the Proposed text. The example claims and the earlier decisions are judged under both rulebooks, and each flipped answer, and each example or earlier decision that comes out wrong under both, is read twice more per side. Only new breaks block (decision P33): PASS needs no example claim that was right under the rulebook in force now wrong, no earlier decision that was right now wrong, and every supporting row as the editor decided; examples are counted like earlier decisions, the ones the rulebook in force gets right. An example wrong under both rulebooks is shown in a row "Wrong before the change" and not counted (the result reads "examples a/a (n more wrong before, not counted)"). Then, in this order:
  1. the Rulebook's When to use is written (with `expect`) and read back;
  2. the new edition is saved and committed (`rulebook edition <edition>: <title>`);
  3. a run of its own sets the rule change Live (`PASS: examples a/a, earlier b/b, yours c/c`) and updates Agent settings;
  4. the follow-up marks the supporting rows Fixed or Still wrong.

  If a stop falls after step 1, the rule is live and the same command finishes without another edition. On FAIL the rule change gets `FAIL: '<claim>' now <answer>` and the rulebook does not change; the distill model's sentence for Editor wording, with its reason (`why`, at most 40 words), goes into the report (as its fourth part, between the table and the Next line, with the tested rule in a block to copy) and `card.md` only. A HOLD (nothing to check against) leaves the rulebook alone too.
- **Rollback.** The rule change must be Live and the rule must still read as that change left it. The lesson's Current text goes back into the Rulebook, a new edition "rolled back <title>" is saved and committed, and the rule change becomes Rolled back.
- **Restore.** `restore.mjs --edition <e> --confirm` writes the When to use of that edition over every tag whose text differs and saves a new edition "restored from <e>" (committed). It is the answer to a drift stop and the way back to any older edition.
- **Adoption.** A tag without rules in force whose row was edited in Notion is not a drift: the next writing command saves a new edition "adopted from Notion: <tag> <columns>" and goes on (`status` only warns). If the new text holds numbered rules the tag is judged from that edition, but only once an engineer lists it in `judge.groups`. Adoption writes the files but does not commit; the next committed edition carries them.
- Commits run `git add agents/claim-tagger-mvp/rubric` and then `git commit -m`, which takes anything else that is staged: keep the index clean before a promote, rollback or restore. Nothing pushes.

## 9. Tests

`node --test tests/mvp/` runs this agent's suite; `npm test` is `node --test tests/` and adds the previous build's.
