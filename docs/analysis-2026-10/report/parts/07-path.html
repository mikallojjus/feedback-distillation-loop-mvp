Path to editors

In short

  • Stages, not dates: housekeeping; the rulebook copy and one tag on {{count:path.firstClaims}} real claims; the walkthrough; then the other tags, one at a time.
  • The editor practises before deciding any real row; the first rows wait in the queue.
  • Every skill report: one sentence, one small table, one "Next:" line.
  • {{count:confirm.items}} checks are still open (Decided and open).

The plan in stages

  • Stage 0, housekeeping and two checks. The engineer limits the access token, makes a read-only dry run and tests the Geo source lookup, after you decide to cut the token's reach; nothing real changes. Done when the new token cannot open the real tables and the repository is pushed.
  • Code changes, after your go-ahead. The engineer makes the {{count:plan.changeSteps}} ordered changes (Technical), each with its tests. Done when the tests pass and the loop runs end to end with a stand-in model.
  • Stage 1, the first real claims. The engineer builds the rulebook copy and runs Context-dependent on {{count:path.firstClaims}} real claims; the machine queues what the judge is unsure about, and the editor decides nothing yet. Done when every write checks out and only Context-dependent rows wait in the queue.
  • Stage 2, the walkthrough. The editor does the walkthrough on a practice page and nothing else; the engineer builds the drafting of first rules, one tag at a time. Done when the walkthrough is done and drafting passes its tests.
  • Stage 3, the first real rows. After the walkthrough, the editor decides the first real rows and approves rules one tag at a time, in the editor's order; the engineer tests the source pass and fixes what breaks. Done when each tag has passed its safety check and the source test has reported.
  • Later. The engineer adds the strict gate, World affairs, the duplicate search, the swap to the real taxonomy and scheduled runs, one at a time. Done when each one's trigger occurs, not before.

The routine

  • The editor types status and tag, then decides as many rows as fit one sitting, lowest confidence first; the rest waits and nothing is lost; the next run adds rows only for new or changed claims. Then distill if decisions blame a rule.
  • As rule owner: approve or rewrite in Lessons waiting, then promote.
  • The engineer: setup and repairs only. The machine: runs unattended.

When more rows wait than fit one sitting (a setting, default {{count:editor.sittingRows}} rows), the status and tag reports give the count and their "Next:" line says "start at the top of Your queue (link)", not "decide the N rows". The first real run is Context-dependent only, so the first queue is tens of rows.

After "Paused" or "usage limit reached", untick Paused or wait, then repeat the command; it resumes.

Guardrails

What keeps the real claims, the editor's fields and the live rules safe; what is kept and dropped is on Safety checks kept. Key: Dn is a decision of the product owner.

  • Allowlist: on the mirror, updates to Agent tags and Agent notes only, checked in the plan, at apply, in the guard hook and in the REST client.
  • Read-back: a filtered pull after every apply; a changed editor field is reported.
  • Drift: the copy is compared with the rubric file at every step; edits to tags without rules are adopted (D23).
  • Pause: the Paused checkbox or a PAUSED file stops every command until a person clears it.
  • Protected ids: the taxonomy, Claims to review, World affairs and the old hub are refused in every plan; the probe proves the token cannot reach them.
  • The guard hook denies every connector page write; gate evidence stops a rule written without a real PASS.

Unchanged hard rules: no script writes an editor-owned field; nothing is appended to the judge prompt; no Notion page is deleted or archived; a check that cannot run is reported, never skipped.
