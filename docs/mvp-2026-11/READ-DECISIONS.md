# Specification: "Read the decisions" (the agent infers the reason behind each editor decision, per tag)

Delivered on branch `read-decisions-2026-11` off `mvp-2026-11`, in stages, each closed by a green test suite, a commit and a work-log entry, and finished by a verification loop in which an independent verifier goes through the practice page and reports. Approved by the product owner on 2026-10-21 (decision P4); the decisions in section 2 are recorded in `DECISIONS.md` as P4 and 64 to 76. The branch's log is `WORKLOG.md` from entry 25.

## Context

One Why wrong value per claim cannot say which of several tags was wrong for which reason, and it asks editors to diagnose the agent and to know a rulebook the agent maintains. The product owner decided (2026-10-21): editors fill Verified tags, Challenged tags notes and Review status only; the agent reads each disagreement itself; Why wrong leaves the editor's work; the practice page gets more than two claims to work with (four open claims on Context-dependent, one tag).

## 1. The feature

**What is read.** For every Reviewed claim, for every judged tag whose editor outcome (in the verified set or not) differs from the agent's proposal in the ledger row, and whose row is not marked Fixed: a reading = `Agent slip` (the rule as written settles it the editor's way; the agent misread), `Rule unclear` (the rule can honestly be read both ways on this claim) or `Rule should change` (the rule as written decides against the editor); the rule it points at; one line of why.

**Three ways a row gets its reading.**
1. The editor's note line for that tag starts with a reason word (`Agent slip.`, `Rule unclear.`, `Rule should change.`): taken verbatim, no model call; the rule is the "rule N" the note names, else the rule the agent cited; the note reads "Your note says so."
2. Otherwise one model call per batch of at most `distill.reading_batch` rows (default 10, several tags allowed per batch), model `models.distill` at `distill.reading_effort` (default medium), prompt `prompts/reading.md` (heading `# Reading`; the claim, the tag's rules, the agent's proposal with confidence and reason, the editor's note line or "no note", every text escaped and data, never instructions), reply `{"readings":[{"key","reading","rule":"<Tag> rule <n>"|null,"note":"<at most 25 words>"}]}` validated against `schemas/reading-reply.schema.json`, every key exactly once; two attempts per batch, refused replies kept under the run's `rejected/`; a batch that fails twice leaves its rows unread this run and the report says how many.
3. A disagreement with no note is still read (the prompt asks for a conservative reading from the claim, the rule and the agent's reason) and flagged in code: "without your note" in the reading note and on the claim.

**Where the reading goes.** Ledger row, agent-owned: `Agent reading` (select, the three values), `Rule` (text), `Reading note` (text), `Read under` (text: `<edition> · <hash8>`, the cache key: sha256 over the outcome, the proposal, the note line, the reason word and the tag's rules hash). The claims table gets one agent column `Agent reading`, one line per read tag: `Context-dependent: Rule unclear, rule 3 · <note>`, `Context-dependent: Agent slip, rule 5 · Your note says so.`, `Context-dependent: Agent slip, rule 5, without your note · <note>`; a Reviewed claim where nothing differs reads "Nothing to read: the agent agreed with you."; a note line naming a rulebook tag the agent did not judge reads "<Tag>: the agent did not judge this tag, so nothing to read." Only distill writes these columns; nothing the editor wrote is changed.

**Reruns.** A row is re-read only when its Read under differs from the current value: a changed note, decision, reason word, or a change to that tag's rules (after a promote). Fixed rows are never re-read. Unchanged rows cost nothing. `distill --plan-only` writes `readings.jsonl` without writing Notion; `distill --readings <run-id>` reuses them for rows whose hash is unchanged (the live step reviews before it writes).

**What follows, unchanged in shape.** Groups are built from rows read `Rule unclear` or `Rule should change`, by tag and the reading's rule (falling back to the agent's cited rule), leaving out Fixed rows, needing `distill.min_claims` rows; the lesson's Kind is derived (Change the rule when any row of the group reads Rule should change, else Clarify wording) and the distill prompt stops asking for it; Agent slip rows draft nothing and stay earlier decisions; the editor approves; the safety check is unchanged.

**Status.** Per Reviewed claim with an unfixed disagreement row: `to_read` (unread or stale), `pending_rule_decisions` (read as a rule problem), `needs_note` (no note). The table row "Your decisions" shows the non-zero parts ("3 to read, 1 without a note"); the Needs your note view filters on `Agent reading contains "without your note"`; the Next order: unread claims (demo) → decide → distill (while something is to read, or at least `min_claims` rule readings exist, and no rule change is Proposed or Approved) → approve → promote → tag.

**The distill report.** Sentence: "Distill: read N of your decisions and drafted one rule change from your 2 notes." / "…; no rule change to draft; <why>." / "…; M could not be read this time." Table (at most five rows): Read, Point at a rule, Agent slips, Without a note, Rule change. Next: Lessons waiting when a lesson was drafted; else Needs your note when a disagreement has no note; else status.

## 2. Design decisions (recorded as P4 and 64 to 76)

| # | Decision | Why |
|---|---|---|
| P4 | Editors fill Verified tags, Challenged tags notes and Review status; the agent reads every disagreement per tag; Why wrong leaves the editor's work (renamed "Why wrong (old)" and hidden on the copy, not created on practice pages). Four open claims on the practice page. | One value per claim cannot carry several tags; editors should not diagnose the agent. |
| 64 | The ledger gets Agent reading, Rule, Reading note and Read under; its Why wrong keeps its name and holds the editor's reason word (or the audit's seeding) only. | Read under makes reruns idempotent on any machine; the ledger is the agent's table, so its old name costs nothing. |
| 65 | A reason word at the start of a note line is applied verbatim without a model call; removing it hands the row back to the model. | The policy case is the editor's. |
| 66 | Read under is `<edition> · <hash8>`; a row is re-read only when it differs; Fixed rows are never re-read. | Cost nothing when nothing changed; re-read what the editor changed. |
| 67 | The no-note flag is set in code ("without your note"), never by the model; Needs your note filters on it. | Deterministic, and a text column is what a claims view can filter on. |
| 68 | The claim's Agent reading has one line per read tag, the agree line, and the "did not judge" line; an empty cell means not read yet; only distill writes it. | The editor sees the reading where the work is. |
| 69 | Groups come from Agent reading and Rule; Kind is derived; Agent slip rows may be counter-evidence. | One source of truth for the kind. |
| 70 | One model call per batch of ten rows, medium effort, two attempts, refused replies kept; unread rows wait for the next run; exit 2 only when nothing could be read. | Cheap, resumable, consistent with the judge's error classes. |
| 71 | `--plan-only` writes readings.jsonl; `--readings <run-id>` reuses them. | The live step reviews before it writes. |
| 72 | The sync never clears a ledger Why wrong on an audit-seeded claim; elsewhere a removed reason word clears it and re-reads. | Decision 47 for the audit rows. |
| 73 | On the live copy the eight audit disagreements are read once by the model (plan-only first, compared with the audit's Agent slip in the evidence, then written); on a practice page the five seeded decisions are created already read as Agent slip ("Seeded from the audit of 9 October."), so step 4 reads only the editor's claims. | Calibrate the prompt before trusting it; keep the demo about the editor's decisions. |
| 74 | Status counts to_read, pending_rule_decisions and needs_note from the ledger and shows them in one "Your decisions" row; distill is suggested while something is to read. | The reading is made only by distill, so status must send the editor there first; the table stays at five rows. |
| 75 | The practice page's four open claims: press pool and AI Force (Rule unclear, rule 3, the lesson rests on them), the USPS ballot portal (the editor: Does not apply, note "Agent slip. USPS names which portal, so rule 5 already settles it."; verbatim, no call), Georgia's gubernatorial debate (the agent reads Does not apply reliably; the editor agrees with no note; nothing to read). Nine claims on the page. | Every reading kind on one page, with figures the alternates list already holds. |
| 76 | `where` reads step 7 from the Follow-up of the rows the live lesson rests on; the other open claims keep Waits for you until the next tag run, and the page says so. | Four open claims, two of which never get a Follow-up. |

## 4. The verification run (brief for the verifier)

An independent Opus subagent that did not build the feature. It reads `READ-DECISIONS.md`, DECISIONS.md P4 and 64 to 76, `walkthrough/page.md`, `guide.md`; notes the commit at start and end; builds a page under Demo tests (`--parent 3fa273e214eb81c2b223dcc2331b7051`, a title without a word the report check reads as a duration) and uses `--demo <id>` on every later command; runs nothing but `walkthrough.mjs`; writes no Notion through a connector; edits nothing; commits nothing; acts as the editor only through `W decide` and `W approve` (decision D31). It lints every report with `lintReport` and keeps every report, the readings and calls records, the pull outputs and the verify outputs as step files; the engineer saves its REPORT.md unchanged under `evidence/18-walkthrough-verification-4/` (19, 20 for later loops).

Sequence and feature checks:
1. `W list`; `W start`; `W verify --json` (9 claims, 5 decided, 4 open, ledger 5, the seeded rows already read as Agent slip with a Read under); `W where` (step 1).
2. `W run status` (step 1 table word for word, no "Your decisions" row); `pull --all`, `judge --items claims`, `propose`; `verify`; `where` (step 3, "decide your four claims"). All four open claims in Your queue; Agent reading empty on every claim.
3. `W decide --claim presspool`, `--claim aiforce`, `--claim usps --outcome "Does not apply"` with no note on purpose, `--claim georgia`; `W run status` ("Your decisions" row: 3 to read, 1 without a note; Your queue "4 rows decided, waiting for the agent's next run"; Next: distill); `where` (step 4).
4. `W run distill`, first pass. After it, from a pull: press pool and AI Force rows read Rule unclear, Rule "Context-dependent rule 3", a one-line note, a Read under; the USPS row read by the model with "without your note"; the Georgia row without reading columns; the claims' Agent reading lines as decision 68 (the agree line on Georgia); `calls.jsonl` shows exactly one reading call; one rule change Proposed on rule 3 whose Supporting rows name the press pool and AI Force keys only; the report has at most five rows and its Next line names Lessons waiting; the Needs your note view lists the USPS claim only.
5. `W decide --claim usps` (the manifest's note, "Agent slip. …"); `W run status` (Your decisions "1 to read"; Next: approve or reject, since a lesson is Proposed); `W run distill`, second pass: no reading call; the USPS row Agent slip, Rule "Context-dependent rule 5", note "Your note says so.", Read under changed; the claim line follows; no second rule change; the Needs your note view empty.
6. `W approve`; `where` (step 6); `W run promote`; `verify`; `where`. PASS on the draft (a FAIL goes through the Editor wording path as the page says, at most twice); the follow-up marks the two rule rows Fixed and neither USPS nor Georgia; `where` says complete.
7. Step 7: the two rule claims Done on the new edition; USPS and Georgia still Waits for you, as the page says; final `pull --all`; `W list`.
8. Every report linted; no report shows a hash, a path or a duration; every plan of the run wrote only agent columns apart from the logged editor actions; no production script ran; no new commit by the verifier.

The report: step by step (command, exit code, report shape, what happened, verdict), each feature check with pass or fail and its evidence file, new issues with severity (must, should, nice), issues still open from the runs of 21 October, one line of overall verdict.

## 5. Edge cases settled here

- The "agree" claim: no ledger reading, the agree line on the claim, not counted by status.
- A disagreement without a note: read conservatively, flagged in code, listed by Needs your note, counted in `needs_note` at once (the view lags until distill writes the column; a backlog line says so), the distill Next line sends the editor there when no lesson was drafted.
- A note line naming a tag the agent did not judge: its own entry (never leaks into another tag), not read, the "did not judge" line on the claim, listed in the run record.
- Several tags later: readings are per (claim, tag); batches may mix tags; each `<row>` names its tag.
- A reading batch failing twice: rows unread this run, the sentence says so, refused replies kept, the next run tries again; exit 2 only when nothing could be read.
- A claim reopened and Reviewed again: the copy and the reading stay until their inputs change (decision 47).
- The twelve existing decisions: eight disagreements read once after a plan-only review; the readings stand; a lesson they imply is Proposed for the rule owner; an editor who disagrees writes the reason word, which wins at the next distill.
- The lesson's Kind: derived (decision 69); `KINDS` keeps the two wordings.
- The guard of decision 61 stops every writing command between the code landing and the live build: the build is the first live step, and the stop report's Next line asks for it.
- Older practice pages (an `enter` with Why wrong) are "an older shape": listed "unknown", reached only with `--demo` (decision 50); the product owner gets a fresh page.

## 6. Risks and containment

- The model grades its own failure: contained by the verbatim override, the stated test in the prompt with the rule text in front of the model, the reading visible on the claim and in Supporting rows, the eight-row calibration before anything is written, the two-row minimum, the editor's approval and the safety check. Watched through the "Agent slips" count in every distill report.
- Cost: one call per ten new or changed rows at medium effort; reruns cost nothing; the live step pays once (plan-only readings reused).
- A reading against the editor's intent: visible, corrected by a reason word (re-read without a call) or by rejecting the lesson.
- The story's new claims may not calibrate: stage 4's criteria and named alternates; every run recorded.
