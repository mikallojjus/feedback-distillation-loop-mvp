# Contracts for `agents/claim-tagger-mvp/` (the shapes every script agrees on)

Written by the orchestrator before the Stage 1 code is built. Coders follow this file; where it is silent, the W3 digest (`sweeps/W3-digest.md`) decides; where both are silent, the coder picks the simplest thing and says so in its report. Plain Node ESM, built-ins only, Windows-safe names (no `:` in generated names), every record validated against a schema before the next step reads it (`lib/validate.mjs`).

`notion.views` (written by setup) holds `{ id, url }` for each view that exists: `your_queue`, `needs_your_note`, `agent_disagreed` (the three on the Claims copy), `your_queue_ledger`, `needs_your_note_ledger` (the two older views of Tag decisions, renamed), `lessons_waiting`, `rulebook`. `validateConfig` refuses a claims entry that lacks one of the seven `columns` (claim, link, sources, is_factual, verified, review_status, notes) or eight `write_columns` names (tags, confidence, reasons, status, waiting, edition, remarks, reading; the message names it), a `columns.why_wrong` or `write_columns.notes` (Why wrong left the editor's work and Agent notes is retired, sections 16 and 17), two keys that name the same column, a claims column that is not listed in `editor_columns.claims_copy`, and an agent column that is. A demo profile's config adds `"demo": true, "demo_id": "<id>"`, points `rulebook`, `claims[0]` and `databases` at the practice page's tables, and lists production's tables under `protected_database_ids`.

## 3. The rubric file (`rubric/rubric.json`), lock, history, changelog

```json
{ "edition": "2026-10-16.1", "built_at": "<ISO>", "source": { "database_id": "...", "data_source_id": "...", "read_via": "connector", "read_at": "<ISO>" },
  "tags": [ { "name": "Context-dependent", "page_id": "<copy row page id>", "category": "Quality", "polarity": "Issue", "status": "Verified",
              "counterpart": "Self-contained", "description": "...", "when_to_use": "<raw text>",
              "rules": [ { "n": 1, "text": "A pronoun with no antecedent ..." } ], "example_claims": ["..."],
              "geo_status": "To be created", "geo_tag_id": null, "verified_on": "2026-09-10", "evidence": "https://...", "work_tags": ["Pipeline benchmark check", "Issue"],
              "capability": "text", "judged": true, "tag_hash": "<h16 of name + rules text>" } ],
  "rubric_hash": "<h16 over the sorted tag hashes>" }
```

- Editions are `YYYY-MM-DD.n` (decision 9). `rubric.lock` holds `{ edition, rubric_hash, locked_at, tags: { <name>: tag_hash }, text: { <name>: when_to_use } }`. `history/<edition>.json` is the full rubric of that edition. `CHANGELOG.md` gets one line per edition: date, edition, what changed and why (a lesson title and PASS, a rollback, an adoption).
- Rules are parsed from When to use: lines starting with `<n>.`; a preamble before rule 1 and a note after the last rule are kept in `when_to_use` but are not rules. The Example Claims column is split one example per line; a leading `- ` and surrounding quotes are stripped; a line that is not a claim (no letters or longer than 400 characters or the known "255 legacy linked claims" line) is dropped.
- `judged = rules.length > 0 && capability === 'text'` (MVP).
- Drift (every command, after `pull`): for every judged tag, compare the copy's When to use, Description, Example Claims and Counterpart with the lock's text; a difference stops with exit 4 and names the tag and the column. For a tag without rules in force, a changed row is adopted: a new edition is written (history, lock, changelog line "adopted from Notion") and the command goes on; if the new text holds numbered rules, the tag becomes judged from that edition (it is still only judged when its group is in `judge.groups`).
- `restore.mjs --edition <e> --confirm` writes the locked When to use of that edition back to the copy for every tag whose text differs (a plan, applied with read-back) and records a new edition "restored from <e>". `rollback.mjs --lesson <title> --confirm` does the same for one tag from the lesson's Current text and sets the lesson Rolled back.

## 4. Canaries and cases (`evals/`)

- `canaries.jsonl`: `{ "id": "canary-<n>", "tag": "Context-dependent", "claim": "...", "expected": "apply" | "do_not_apply", "source": "example claims of Context-dependent" | "example claims of Self-contained" }`. Eleven rows at setup (6 apply, 5 do not apply). Built by setup from the taxonomy file; frozen until a rule change.
- `cases.jsonl`: the earlier decisions, synced from decided queue rows by pull: `{ "key": "<geo_id>::<tag>", "tag", "claim", "outcome": "Applies" | "Does not apply", "why_wrong", "decided_edition", "source": "audit of 9 October" | "queue" }`.

## 5. Pulls (`runs/pull/<pull-id>/`)

`pull.mjs` (reads only) writes `schema/<table>.json` (retrieveDatabase), `raw/<table>.jsonl` (pages), `norm/claims.jsonl` `{ table, geo_id, page_id, notion_url, claim, geo_url, sources_text, source_links, is_factual, agent_tags, agent_status, tags_waiting, agent_confidence, agent_reasons, agent_edition, agent_remarks, verified_tags, review_status, why_wrong, challenged_notes, last_edited }` (the three relations Agent tags, Tags waiting and Verified tags are resolved to tag names through the page ids of the Rulebook copy rows of the same pull, else those in `rubric/rubric.json`; an id that names no tag is left out and said in a warning; section 16; `schemas/claim-row.schema.json`), `norm/rulebook.json` (the copy rows as rubric tags, un-hashed), `norm/queue.jsonl` (the 13 columns of the ledger, Tag decisions, plus `page_id`, `last_edited`, `decided` boolean; `schemas/ledger-row.schema.json`), `norm/lessons.jsonl` (10 columns plus `page_id`, `created`, `supporting_keys`), `norm/settings.json` `{ page_id, paused, rulebook_edition, last_run_summary }`, `drift.json`, `requests.jsonl` (the request log), `pull.json` (manifest) and `runs/pull/LATEST`. Flags: `--tables a,b` or `--all`; `--source real_claims --dry-run` pulls the real table into `runs/dry-run/<run-id>/` (schema, every row, `report.md` with row count, column types, how Geo Sources parses, `requests.jsonl`) and nothing else. A row that does not fit its schema is a warning, not a stop. `pull.mjs` exports `decisionsFor` and the other pure functions of `lib/decisions.mjs` (section 15). A pull of a paused agent still completes (the caller decides). Duplicate keys within a table: exit 2.

## 6. The cell store (`runs/judgments/<key16>/`)

Key: `h16(pyJson({ driver, model, effort, pass: "text", prompt_version, group, tags: [{ name, tag_hash }] sorted by name }, { sortKeys: true }))`. `meta.json` holds those inputs. `run-1.jsonl`, `run-2.jsonl`, `run-3.jsonl`: one line per item `{ "id": "<geo_id>", "item_hash": "<h16 of the claim text>", "status": "ok" | "error", "tags": [ { "name", "decision": "apply" | "do_not_apply" | "ask_editor", "p": 0..1, "rule_ref": "Context-dependent rule 3" | null, "reason": "<= 40 words" } ], "call": { "run_id", "batch", "attempt", "cli_version", "usage": { "input", "cache_write", "cache_read", "output" } } }`; the last line for an item wins. A rule change changes the tag hash, so the group gets a fresh store; the old one stays as history.

Judge reply JSON (one call per batch): `{ "items": [ { "id": "<the id given in the claim block>", "tags": [ { "name", "decision", "p", "rule_ref", "reason" } ] } ] }`, validated against `schemas/judge-reply.schema.json` (every id of the batch present once; every judged tag of the group present once per item; `p` a number in [0,1]; names from the group). An invalid reply gets a second attempt for the batch (`attempts_per_batch` 2); after that the batch's items are `status: error` for that run. Each refused reply is kept as it came in `runs/<run-id>/rejected/batch-<n>-attempt-<k>.md`, with the problems listed.

Adaptive runs (decision D19): run 1 for every item; a cell is unsure when its decision is `ask_editor` or its `p` is strictly inside the band; items with an unsure cell are candidates for run 2, at most `max_share` of the run's items, lowest margin first (margin = the smallest `|p - 0.5|`; `ask_editor` counts as 0); run 3 only when runs 1 and 2 disagree. Candidates beyond the cap are marked `capped` in `run.json`.

Error classes (decision 14): a reply matching the usage-window wording stops the run with exit 75 and writes the resume command into `run.json` and `report.md`; a transient error waits `backoff_ms[k]` and retries, and the third transient failure in a row stops the run with exit 1 and the same resume command; a validation failure uses the second attempt. Every call is one line in `runs/<run-id>/calls.jsonl` `{ group, batch, items, attempts, usage, duration_ms, cli_version, status }`; nothing in an editor-facing report shows durations, call counts or dollars.

## 7. Verdicts (propose)

Per cell, over the runs it has: `decision` by majority (`ask_editor` wins any tie), `p_mean`. Unsure when any run is `ask_editor` or `error`, when the runs are not unanimous, or when `p_mean` is strictly inside the band. `Agent proposal`: Applies when not unsure and the majority is `apply`; Does not apply when not unsure and the majority is `do_not_apply`; Can't tell otherwise. `Agent confidence` = `max(p_mean, 1 - p_mean)` rounded to two decimals (0.5 is a coin flip). `Agent reason`: the reason of the last run shortened to `reason_max_words` words, then " · <rule_ref> · <k> of <n> runs agree".

The tag step (`propose.mjs`) writes, through one plan (revision of 21 October; `CLAIMS-REVIEW.md` sections 3 and 6 are the specification, section 16 below the contract):

- **On every judged claim** of the Claims copy, the agent's seven columns, each only where it differs from the pulled value: `Agent tags` and `Tags waiting` (relations to the Rulebook copy, written as the page ids of the tags' rows), `Agent confidence` (the lowest confidence among the claim's judged tags, 0.5 to 1), `Agent reasons` (one line per judged tag, `<Tag>: <the Agent reason text>`, the text of the ledger's Agent reason: the reason, the rule cited, "<k> of <n> runs agree"; the follow-up rewrites the lines of the tags it checks again and keeps the others), `Agent status`, `Agent edition` and `Agent remarks`. A claim the judge has not read keeps its columns.
- **In the ledger (Tag decisions)** a row per judged claim and tag: created when missing (every judged cell, not only the unsure ones), updated when the proposal, the confidence, the reason or the edition changed. The proposal columns of a row that is decided (it holds a Tag outcome) or whose claim is Reviewed are never rewritten: they are what the editor saw.
- **On a Reviewed claim** the copy of the decision in the ledger row (`decisionsFor`, section 15): Tag outcome, Why wrong, Your reasoning, Decided under. A row is written only where a copy differs; Decided under keeps the edition once recorded.

On a claim that is not Reviewed, `Agent tags` holds the tags whose proposal is Applies and `Tags waiting` the tags whose proposal is Can't tell; a tag with no verdict in this run keeps its place in both. On a Reviewed claim `Agent tags` is the editor's verified set, whatever the agent proposed (a sure proposal that differs from the editor's decision is never applied) and nothing waits. A claim whose Review status is To review (the editor's mark, or QA's on the real table) waits on every judged tag whatever the confidence and none is written to `Agent tags`, so it lands in Your queue on the next run. `Agent status`, `Agent edition` and `Agent remarks` follow section 16; the report's rows and Next line are as before, and "N wait for you" counts the claims whose Agent status is Waits for you and whose Review status is not Reviewed.

Before it plans a write, the tag step (and the follow-up, promote, distill and status) checks the pulled schema of the Claims copy: the seven agent columns and the editor's four must exist with the types of section 16 (`needClaimColumns` in `lib/loop.mjs`). A table that `setup.mjs build` has not rebuilt still has the text column Agent tags and the relation under its old name; the run then stops with exit 2 and a report whose Next line asks for the setup build, and does nothing. Without the check a decision would be read from a column that is not there and every Reviewed claim would look decided as Does not apply.

A decided ledger row whose claim is not Reviewed (the setup has not yet carried the earlier decisions over) is a warning of the run, not a decision.

## 8. Plans, apply, ledger, read-back (`lib/plan.mjs`)

Every script that writes Notion builds `runs/<run-id>/plan.jsonl` first: a header line `{ "plan": { "run_id", "script", "created_at", "rubric_edition", "counts": { "creates", "updates" } } }`, then one op per line `{ "op": "create" | "update", "table": "tag_decisions" | "rule_changes" | "agent_settings" | "rulebook" | "claims_copy", "key": "<row key>", "page_id": "<update only>", "properties": { "<Column>": <plain value> }, "expect": { "<Column>": <plain value> }, "children": [ <blocks> ] }`. `checkPlan` runs before any request: the table must be one of the config's own tables; every property must be in the table's writable set (tag_decisions: Claim, Key, Tag, Agent proposal, Agent confidence, Agent reason, Claim link, Rulebook edition, Follow-up, and the copies of the editor's decision: Tag outcome, Why wrong, Your reasoning, Decided under; rule_changes: Lesson, Tag, Rule, Kind, Current text, Proposed text, Safety check result, Supporting rows, Status with values Proposed, Live, Rolled back; agent_settings: Rulebook edition, Last run summary, plus Name on a setup create; rulebook: When to use, plus every column on a setup create; claims_copy: the seven agent columns of section 16 (Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks), plus every copied Geo column on a setup create); an editor column (claims_copy: Verified tags, Review status, Why wrong, Challenged tags notes; rule_changes: Editor wording; agent_settings: Paused; tag_decisions has none) is refused unless the plan is a setup plan seeding the audit (a create or an update of a claim whose Challenged tags notes start with "From the audit of 9 October": the `migrate-decisions` step), or the config is a demo profile and `runs/SETUP` exists (the decided claims of a practice page at creation), or `checkPlan` is called with `demoEditor: true` on a demo profile directly under `runs/demos/` (then updates of the four claims columns, Editor wording and Status Approved or Rejected are allowed: the editor actions of `walkthrough.mjs`, decision 31). Protected ids are refused anywhere in a plan. `applyPlan` sends the ops in order through the REST client (version 2022-06-28; `expect` is checked against the pulled value before an update and the op is skipped with `skipped: expect` when it differs), appends `ledger.jsonl` `{ op_index, key, page_id, status: "done" | "failed" | "skipped", read_back: "ok" | "mismatch", error, at }` after each op, reads every written page back and compares the plain values, and ends with exit 2 when any read-back mismatched. `--plan-only` stops after `checkPlan`. A `create_uncertain` error stops the apply; the next run of the same script reads Notion first and resumes by key (never a second create for a key that exists).

## 9. Reports (`lib/report.mjs`, `runs/<run-id>/report.md` and `report.json`)

Every script ends by writing `report.json` `{ "demo": false, "sentence": "...", "rows": [["What", "Now", ""], ...] (at most 5 rows of 3 cells; omit when nothing to count), "next": "Next: ..." }` and `report.md`, the three parts in order with one blank line between them: the sentence (prefixed "Demo · " when `demo` is true), the table (a Markdown table with a header row; omitted when `rows` is empty), the Next line. Nothing else: no headings, no file paths, no run ids, no durations, no call counts, no dollars, no JSON, no time estimates (no minutes, hours, days, weeks); dates are allowed ("16 Oct 11:20"). When more open queue rows exist than `queue.sitting_rows`, the sentence gives the count and the Next line is `Next: start at the top of Your queue (<link>)`. After a stop (exit 1 or 75) the Next line is the same slash command. The skill prints `report.md` verbatim first. When the Next line sends the editor to Notion it adds one checklist after the report (decision 58; the lists are in `.claude/skills/claim-tagger/references/guide.md`), and nothing else: after the Next line and one blank line, one numbered list (1., 2., ...) of at most five lines, one item per line, with no heading and no words before or after it. The report itself stays the three parts above; the report lint (`lintReport`) is applied to the report alone, and its word rules (`lintWords`: no file path or script name, run id, duration word, dollar sign, JSON brace, shorthand code, and the words database, rubric and gate) to every line of the checklist too. The headless checker (`transcript-check.mjs`, graded by `headless-check.mjs`) accepts a final message that is the report alone or the report and such a checklist, and fails anything else after the Next line, a second list included. Templates and examples: `docs/analysis-2026-10/debate/inputs/report-examples.md` and W4 digest section 8.

## 10. Run folders and ids

`runId(kind)` gives `YYYYMMDDTHHMMSSZ-<kind>`; every script writes `runs/<run-id>/run.json` `{ run_id, script, args, started_at, finished_at, exit_code, rubric_edition, pull_id, resume: "<the exact command to continue>" }` first (started) and last (finished); for a run whose state folder is a practice page (a folder directly under `runs/demos/`), `resume` goes through the runner, `node agents/claim-tagger-mvp/scripts/walkthrough.mjs run --demo <id> <script> <arguments>` (`lib/resume.mjs`), because the bare line has no `CLAIM_TAGGER_MVP_ROOT` and would run on the production tables. every script runs `preflight` (lib/preflight.mjs) first: it refuses with exit 3 when `runs/PAUSED` exists or Agent settings' Paused is ticked in the newest pull; warns when `runs/SETUP` exists; stops with exit 4 on drift; stops with exit 4 on a model mismatch reported by the CLI wrapper.

## 11. Exit codes

0 ok; 1 error (a resumable stop: the report's Next line repeats the command); 2 invalid (a plan, a reply or a read-back failed validation; a duplicate key); 3 paused; 4 drift or model mismatch; 5 reserved; 10 HOLD (nothing to evaluate); 11 FAIL (the safety check); 75 usage window (resume later).

## 12. The fakes (`tests/mvp/fixtures/`)

## 13. Editor-facing words

table (not database); Your queue (the view of the Claims copy that lists the claims whose Agent status is Waits for you; the older views of Tag decisions are "Your queue (ledger)" and "Needs your note (ledger)", engineer words); ledger (Tag decisions, the agent's own record; engineer word, the practice page says "the agent's own record of each decision"); rulebook and Rulebook copy; edition and "Rulebook edition"; safety check and "Safety check result"; practice page; canaries are called "examples" in anything a person reads. No personal names anywhere a person reads. No shorthand codes.

## 14. Decisions taken by the coders and adopted (2026-10-15)

- `rubric.lock` has a fourth key `columns { <name>: { Description, "Example Claims" (parsed, one per line), Counterpart } }`, because drift compares four columns.
- `computeDrift(lock, rows, { config })`: a tag is judged when its locked text holds rules and (with a config) it is a text tag in a judge group; otherwise a change is `adopted`. `added` and `missing` hold names; `judged` holds one entry per differing column.
- Reports: `header` is its own field (default `["What", "Result", ""]`), `rows` are body rows; the lint also requires a one-line first sentence and exactly one Next line, last. Text inside double quotes (straight or curly) is exempt from the word and character rules, so scripts quote claim text in sentences and cells. "second" counts as a time word.
