# Decisions taken alone between checkpoints

One line of reason each. The product owner's decisions D1 to D35 live in `docs/analysis-2026-10/DECISIONS.md` and are not repeated here.

| # | Decision | Reason |
|---|---|---|
| 1 | The untracked inputs (`docs/analysis-2026-10/`, `MVP-PROMPT.md`, `.claude/agents/editor-persona.md`) are committed as the branch's first commit. | A session that loses its context must find the brief and the designs in git, not only on disk. |
| 2 | Haiku sweep digests are written to `docs/mvp-2026-11/sweeps/` and only summarised back. | The digests replace reading the 180 KB of designs and survive context loss. |
| 3 | There is no unpause command and no `--unpause` flag anywhere. | Hard rule 7: a person clears Paused and `runs/PAUSED`; the agent never does, so nothing needs an allow rule. |
| 4 | `rollback` and `restore` are separate scripts listed only under `ask` in the settings; every other script is allowed by name. | Bash allow rules match a prefix, so a dangerous flag on an allowed script could never ask; separate scripts can. |
| 5 | Settings: the new folder's read and loop scripts are allowed by name; `setup`, `rollback` and `restore` are under ask; the old folder's writer scripts are denied; connector tools are listed under both server names (`claude_ai_notion` and this session's id). | Setup is a one-time structural write that could never be undone (hard rule 8); the connector's server name differs between sessions. |
| 6 | The guard's registry of builder-created pages and tables lives in `runs/builder/`, not `runs/setup/`. | Windows paths are case-insensitive: `runs/setup/` would collide with the `runs/SETUP` marker (found by the guard's own test). |
| 7 | Connector writes are allowed only while `runs/SETUP` exists and only on registered targets: content pages (the proposal, practice pages) go through the connector; tables, rows and views go through the REST client. | Rich page content is a connector strength; rows and tables stay under the plan-and-apply rule. |
| 8 | The copy's relations: one dual relation between the Claims copy's "Claim quality tags — verified" and the Rulebook copy's "U.S. Politics debate claims"; "World affairs debate claims" and "Editors challenging the QA tags" are left out. Shown as a deviation in the structure proposal. | A relation must point at a table; the World affairs and editors tables have no copy and are protected. |
| 9 | Editions are dated: `YYYY-MM-DD.n` (the first edition at setup is the setup date plus `.1`; a later change the same day gets `.2`). | The brief fixes the format; the design's "version 1" and "2026-10-15.2" were two conventions for one thing. |
| 10 | Duplicate tags (Exact duplicate, Semantically duplicated) are never judged and never queued in the MVP; no exact-text check either. | Only Context-dependent is judged (decision D35); the within-table text check is a backlog item. |
| 11 | The sitting size (`queue.sitting_rows`, default 20) lives in `config.json`, not in Agent settings. | The brief lists three Agent settings columns; a config key is enough for one editor. |
| 12 | Rule changes has no Lesson ID column; a lesson is identified by its title, which distill keeps unique. | Fewer moving parts and no code-like ids in front of the editor. |
| 13 | Both copies leave the relation columns out (supersedes decision 8): the Rulebook copy has no relations to claims tables, the Claims copy has no relation to the rulebook or the editors table. | The W3 design leaves them out; a relation would have to point at a protected table or add a synced column nobody uses. |
| 14 | Error classes in model calls: a reply that fails validation gets a second attempt per batch; a transient error (rate limit, overloaded, timeout) is retried with backoff and after three in a row the run stops with exit 1 and its resume command; only the CLI's usage-window wording stops the run with exit 75. | The brief: a transient error is never treated as the window; "two attempts per batch". |
| 15 | No separate apply script: every writing script builds its plan file, validates it against the allowlist, applies it with a ledger and reads every write back in the same run; `--plan-only` stops after the plan. | Hard rule 1 is about the plan existing before the write, not about a second command; one command per step keeps the skill simple. |
| 16 | Rollback restores the lesson's Current text (the text in force before its PASS), records a new edition and marks the lesson Rolled back; the rulebook history holds every edition's text. | The design names the functions but not the source of the restored text. |
| 17 | Safety check verdict: PASS when every canary passes, no earlier decision newly fails and every supporting row comes out as the editor decided; otherwise FAIL; HOLD (exit 10) only when there is nothing to evaluate; FAIL is exit 11. | The design lists the conditions without the combining rule. |
| 18 | Canaries: the six example claims of Context-dependent (expected Applies) and the five example claims of its counterpart Self-contained (expected Does not apply), read from the taxonomy at setup. | The walkthrough design counts 11 canaries (6 apply, 5 do not apply) without naming them; the counterpart's examples are the natural negatives. |
| 19 | The taxonomy's 13 rows are read once through the connector and saved to a file that the setup plan writes from; the real claims table is pulled once through the REST client with a request log. | The brief says so for both; the REST token was checked and reads both tables, so the request log can prove "reads only". |
| 20 | The Claims copy carries the real table's thirteen Geo columns plus Agent tags and Agent notes; the six review columns and the two relations are left out. | The loop reads the Geo columns only; the review columns belong to the QA process on the real table. Shown as an open point in the proposal. |
