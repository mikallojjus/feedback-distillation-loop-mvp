Claim tagger MVP

The first working version of the claim tagger's feedback loop: where it stands, how to run it, the tables it keeps in Notion and what waits for later.

Status

In short

The MVP is built, tested and run live: the second checkpoint, the final demo, is reached. The loop runs end to end on a copy of 50 real claims in Notion: the agent tags, the editor decides, a rule change is drafted from the decisions, a safety check tests it against every earlier decision before the rulebook changes, and the follow-up re-checks the rows. The whole cycle ran 5 times on practice pages, through to a rule going live and being rolled back again. After the demo was handed over, the product owner asked that editors decide where they work: since 16 October the decision lives on the claims table itself, in the same columns the real table has, and the former queue is the agent's own record.

The MVP judges one tag, Context-dependent, and never writes the real claims table. Everything else waits in the Backlog.

What the product owner does now. Run the seven steps on the fresh practice page, as the How to run tab describes, and say whether the MVP is agreed.

How to run

In short

You type 4 commands yourself: status, tag, distill and promote. The follow-up runs by itself after a PASS, and the engineer sets things up and fixes what breaks. Every command ends with the same short report in three parts, and a practice page lets you try all of it before you decide a real row.

Built and run. Every command below ran today against the Notion copy, and the whole cycle ran 5 times on practice pages. Commands go into Claude Code, opened in the project folder.

The seven steps, on a fresh practice page

The practice page has its own small tables, so nothing real changes. Build one, then follow the steps written on the page itself; each step has the same four parts: Goal of the step, Existing status, Doing the work and Explaining the outputs.

  1. Open your practice page "Claim tagger practice · product owner, 21 Oct afternoon" under Demos; it was built for you on 21 October after the fixes below, and it is the page the demo commands reach. To make another one later, ask Claude Code for a practice page and paste the link of the Demos page: /claim-tagger-walkthrough with the link.
  2. Type /claim-tagger demo status (step 1 of the page).
  3. Type /claim-tagger demo tag (step 2): the agent reads the 7 claims and fills its side of your 2 rows.
  4. In Notion, in Your queue on the Claims table, decide your 2 claims (step 3): tick the tag in Verified tags where it applies, choose Why wrong, write your note, set Review status to Reviewed. The page gives you the words as a checklist, and Claude repeats it after the report. A decided claim stays in Your queue until the agent's next run picks it up.
  5. Type /claim-tagger demo distill (step 4), then approve the draft in Lessons waiting (step 5).
  6. Type /claim-tagger demo promote (step 6). On a PASS the follow-up runs by itself and step 7 shows your rows marked Fixed. On a FAIL the report hands you the whole text for Editor wording: paste it, then type the same command again.

At any point, "where am I in the claim tagger demo" tells you the step you are at and the one thing to do next.

What you type

You type each command in Claude Code. At this stage one person is both the editor and the rule owner. Each command on the practice page is the same command with demo in front, and acts on the newest practice page.

If it stops because your Claude allowance ran out, wait and run the same command again: it picks up where it stopped. If it says the rulebook text was edited by hand, put the text back as it was, or ask the engineer.

Who does what

  • The editor types status and tag, then decides the claims in Your queue, least sure first: Verified tags is the decision, Review status Reviewed closes the claim, Why wrong and a note say when the rule, not the agent, was at fault. After each report Claude adds a short checklist of what to do in Notion and the next command.
  • The rule owner approves or rewrites lessons in Lessons waiting, then types promote.
  • The engineer does the setup, the rollback and the repairs, and nothing else.
  • The machine runs the follow-up after a PASS, without anyone typing.

Every command ends with the same three parts

  1. One sentence about what ran and what came out.
  2. One small table of at most five rows and three columns. It is left out when there is nothing to count.
  3. One line that starts with "Next:" and names exactly one thing to do: a command, or a Notion link and the action.

Nothing else is added: no run records, no durations, no costs. When more rows wait than fit one sitting, the Next line says "start at the top of Your queue". A report that comes from the practice page starts with "Demo ·" and names the page.

1 · What ran. Demo · Promote: PASS, rule 3 now uses your approved wording (edition 2026-10-15.2), and the follow-up marked both of your rows Fixed (practice page Claim tagger practice · calibration 5).

What the practice page holds

/claim-tagger-walkthrough builds a fresh practice page under a Notion page you name; without a link it asks one question: "Under which Notion page should the demo go? Paste a link." The page has its own small tables, so nothing real changes, and you can build a new one whenever you want to practise again.

The page tells a small story about the Context-dependent tag and its rule 3 on descriptive references: 2 claims wait for you, 5 earlier decisions stand, and 10 example claims guard the safety check. The agent calls the press pool claim Context-dependent and you say that everyone knows the press pool; the agent cannot decide the AI Force claim and you say that a capitalised name nobody knows still needs context. Your two notes become one clearer rule 3.

After the second checkpoint the product owner asked that editors decide tags where they work, on the claims table, as on the real table. The sections below this one are the approved proposal of 15 October and stay as history; this section is what is built from 16 October on, and the specification is in the notes (decisions P2, 42 and 43).

Claims copy carries seven agent columns and four editor columns (the feedback round of 21 October, decision P3, replaced the two-line Agent notes by columns a view can filter on and made Agent tags a relation). Rulebook copy

The 13 rows of the taxonomy table "Claim Tags — verified" whose Work tags contain Issue, with the same column names and types: Context-dependent, Exact duplicate, Factually challenged, Improper capitalization, Improperly sourced, Incorrect grammar, Multi-sentence, Poor wording, Semantically duplicated, Source inaccessible, Trailing period, Unsourced, Wordy. Only Context-dependent is judged in the MVP; the other twelve rows are there so the rulebook is complete and the next tag is a switch, not a rebuild.

Who fills what: setup copies the 13 rows once; the team may edit any column by hand; the agent writes exactly one column, When to use, and only after a safety check PASS or a confirmed restore to an earlier edition. A hand edit to the When to use of a tag that has rules stops every command until the text is put back.

Words

  • Table: a Notion table of rows and columns; this page holds five.
  • Queue: the Tag decisions table: the answers the agent is unsure about, for the editor to decide; Your queue shows the ones that wait.
  • Rulebook: the numbered rules for each tag, kept in When to use in the Rulebook copy; it changes only after a safety check PASS or a restore.
  • Edition: the rulebook's version, a date plus a count (2026-10-16.1); it goes up when a rule changes.
  • Safety check: the test a rule change must pass before it is used: the example claims, the earlier decisions and the change's own rows (yours) must all come out right.
  • Practice page: a page under Demos where an editor runs the whole cycle once on sample claims, without touching anything real.
  • Agent proposal: the agent's answer for one claim and one tag: Applies, Does not apply or Can't tell.
  • Tag outcome: the editor's decision on a row; it always wins over the agent's answer.
  • Why wrong: the editor's reason: Agent slip (the rule is fine, no change), Rule unclear (the agent drafts a clearer rule), Rule should change (the agent drafts a changed rule).
  • Follow-up: after a PASS, the agent re-checks the rows the change rests on and marks each Fixed or Still wrong.

Open points: the relation columns of both copies are left out; the real claims table's six review columns are left out; only Context-dependent is judged, and the other twelve tags wait in the rulebook.
