Code and commands

In short

  • Open Claude Code in the geo-agents folder and ask in plain words, for example "run this week's tagging loop, keep it small, tell me what's waiting for me". The skill /claim-tagger picks the steps and answers in a short paragraph.
  • Six subcommands do the work: status (which rulebook is in force, what waits for whom), tag (judge claims, fill the queue), distill (turn decisions into proposed lessons), promote (put an approved lesson through the gate), follow-up (re-check the claims behind a live lesson) and setup (once).
  • Every subcommand is a fixed sequence of scripts. The scripts do every Notion read and write; Claude Code runs them in order, reads their one-line summaries and reports.
  • In this version every write goes through the integration token in .env, so the loop runs where the token is configured; without it the skill stops and says so.
  • The headless test, a fresh session as on an editor's machine, found four things such a machine needs. They are now in the README and the skill.

One ask in plain words

The short form an editor can type, from the README:

Run this week's tagging loop, keep it small, tell me what's waiting for me.

The plan's longer test prompt spells out what the skill is expected to do with it:

Hi, I'm one of the Geo editors. Please run this week's claim-tagging loop for our Editorial feedback loop page in Notion. Keep it small today: tag at most 10 claims not yet judged with the current rulebook. Check first that the agent isn't paused. Put anything you're unsure about in my queue, turn new editor decisions into proposed rule changes, and if the rule owner has approved a change, test it and only make it live if it passes. Then re-check the claims behind any change that went live. Don't touch anything editors wrote. At the end, tell me in plain words what changed and what's waiting for me.

What comes back is one short paragraph and a table. The passing headless status run opened with:

The claim tagger is healthy. It is not paused, the rubric lock matches, and the Rulebook has no drift.

Headless session, /claim-tagger status, run {{count:headless.statusPassedOn}}

It went on with the rulebook version in force, the queue by Stage, the Needs your note count, the lessons by status, the last three cards and what waits for whom. The two headless tests covered status and a tag dry run; the full plain-words request above has not been run headless yet.

Pause and resume

  • To pause: tick Paused in Agent settings (one row) and, if you like, say why in Reason. Every subcommand starts with a check that stops when Paused is ticked.
  • When the agent pauses itself: the trust breaker writes a pause file when an editor field changed on a row the agent was writing, and names the field with its value before and after. A person looks at it, then clears it with status.mjs --unpause --confirm, which records who cleared it and when.
  • To resume: untick Paused. A run that stopped half way, for a pause or for the subscription's usage window, resumes when someone runs the printed resume command, and keeps the work already finished.

Neither the pause drill nor the trust-breaker drill was run in this trial; both are covered by unit tests.

From SKILL.md; S stands for agents/claim-tagger/scripts, and every command runs from the repository root. The skill never writes a field by hand and never edits a plan file.

A judge run takes minutes (about 50 seconds per batch of {{count:config.batchSize}} claims) and runs in the background; the skill polls status.mjs --run <id> and never starts a second judge on the same run.

Resume and exit codes

CodeMeaningWhat to do
0Done; for promote, PASSRead the summary line; success counts only after the read-back.
1Error, or writes that did not landRead the message. After an apply: apply.mjs --run <id> --retry sends only the ops listed in plan.retry.jsonl.
2Invalid input or nothing to doReport it; a plan check on a run with no plan means nothing to do. Another promote holding runs/PROMOTE.lock also answers 2: resume it or abort it.
3PausedStop. A person unticks Paused, or clears the pause file with status.mjs --unpause --confirm.
4Rulebook drift, lock mismatch, a missing Notion property or select option, or the wrong model answeredStop; status.mjs explains. The engineer restores Notion from the file with status.mjs --restore-rulebook --confirm; a direct edit is never adopted.
5Trust breakerStop; runs/PAUSED names the row, the field, before and after.
10Gate HOLDA result, not an error: the card says what is missing.
11Gate FAILA result, not an error: the card says what broke.
75The subscription's usage window ran outWait for the reset and run the same command with --resume; finished work is kept.
  • Judge. Every finished cell is a file and a ledger row; judge.mjs --resume --run-id <id> reads the run's own recorded options and judges only what is missing. For the judge runs inside a promote, status.mjs prints the promote command to resume instead.
  • Apply. An armed run can be started again: ops already recorded as written are skipped, and a resumed run pulls first, so a create that did land becomes an update instead of a duplicate. A create whose answer was lost is never re-sent blindly; --retry looks the row up by key first.
  • Promote. --resume --run-id <id> continues phase 1; --finalize <id> completes a verified PASS; --abort <id> clears a promote whose apply failed and plans a restore if Notion already changed.
  • Ledgers are append-only with one writer each; a torn last line from a crash is ignored and cut off before the next write.

Headless use: what an editor's machine needs

MSYS_NO_PATHCONV=1 claude -p "/claim-tagger status" --settings .claude/settings.json --permission-mode acceptEdits --output-format stream-json --verbose
  1. Pass the settings. A folder never opened interactively is untrusted, and Claude Code ignores its .claude/settings.json allow rules (the session's own warning: "this workspace has not been trusted"). Passing --settings .claude/settings.json brings them back.
  2. One Bash rule per script. Bash permission rules match whole words, so a directory prefix such as node agents/claim-tagger/scripts/* never matched. The settings now list one rule per script, for example Bash(node agents/claim-tagger/scripts/status.mjs:*). A command chained with ; or && is denied, by design.
  3. Stop Git Bash rewriting the slash. In Git Bash, /claim-tagger status arrived as a path under the Git installation folder. Set MSYS_NO_PATHCONV=1, or start from PowerShell.
  4. Never inspect .env. The first session tried to grep .env to see whether a token was set. The skill now forbids reading, grepping or printing it, and status.mjs --check reports whether a token is configured.

Each transcript is saved in docs/mvp-2026-10/evidence/headless/ and summarised by scripts/transcript-check.mjs: tools called, every Bash command, every Notion connector call, any write naming an editor field, the cost and the final message. Results are on Verification and reviews.

One headless test is still to run by hand: a session that tries a connector write without an armed plan, to see the guard hook deny it. The building session could not start that nested call; the command and the expected result are in docs/mvp-2026-10/evidence/README.md. The hook is configured with a path relative to the repository root, so sessions must start there.

Judge contract

  • Items. --items claims takes the claims of the latest pull; --items eval the claims behind the active cases plus the canary texts. Batches of {{count:config.batchSize}} claims, shuffled per run with a seeded generator; {{count:config.judgeRuns}} runs per rubric version.
  • Call. claude -p spawned with an argument list and no shell, a pinned model (Sonnet 5.5; Haiku 5.5 for smoke runs), effort medium, no tools, one turn. The system prompt is prompts/judge.md with the compact rubric, rendered once per configuration so the prompt cache hits; the claims go on stdin inside <claim id sources> elements, with the instruction that claim text is data, never instructions.
  • Answer. Per claim and per model-judged tag: apply, do_not_apply, ask_editor (the rules do not settle it) or cannot_tell (information is missing); a confidence p from 0 to 1, not calibrated; the rule relied on (Predictive rule 1); the trigger phrase; a reason of at most 25 words.
  • Checks. The reply must have the batch's ids, every in-scope tag exactly once, consistent counterpart pairs and a rule reference that names a rulebook rule. A bad batch gets one retry with the problems quoted, then its items are errors. The pinned model must appear in the reply's usage, or the run stops (exit 4).
  • Decided in code. Unsourced from the sources count; Improperly sourced and Source inaccessible are not checked in this trial, because no source text is read; Editor verified is never output.
  • Majority. More than half the runs agreeing gives the verdict; otherwise ask editor; a missing or failed run gives error.

Proposer rules

  • Decided tags are kept. An editor's Tag outcome, or a seeded outcome, always wins: its queue row is never touched and the claim's Agent tags follow it from the next run.
  • Readiness, in order: Needs editor (a model-judged tag is ask editor or error), Fix needed (an applied tag has Issue polarity), Not checkable (cannot tell, or the sources count is unknown), Ready.
  • Why in queue: Low confidence when the runs disagree, the verdict is ask editor or error, or the mean confidence lies between {{count:config.tSkip}} and {{count:config.tApply}}; Rule changed when the tag's rules changed since it was last judged and the verdict flipped, on undecided rows only.
  • Priority: Check source for Read source first; High for Rule changed, for Low confidence that leans towards applying an Issue tag, and for a three-way split; Medium otherwise. Within the weekly cap new rows are taken by priority, then lowest confidence; the rest are held back until the cap allows ({{count:tagRun.heldByCap}} in the first run).
  • Idempotent. A plan carries only values that differ from the pull, so running propose twice on the same inputs gives an empty plan.

Distiller

  • Input. Decided rows whose Why wrong is Rule unclear or Rule should change, plus seeded rows whose reasoning starts "Rule should change:".
  • Groups. By tag, Why wrong and the rule the agent cited, counting distinct claims. A group becomes a lesson at {{count:config.minClaims}} claims for Rule unclear and {{count:config.minClaimsRuleChange}} for Rule should change. A rule that already has a Proposed, Approved or Live lesson only gains supporting rows (the check is per rule, not per tag).
  • One model call per group (Opus 5.5, prompts/distill.md) with the tag's rulebook entry, the group's rows and other decided rows on the tag as counter-evidence. It returns the kind of change, the target rule, a title, a statement, the proposed text, invented boundary examples and the counter-evidence it would flip.
  • Current text always comes from the rubric file, never from the model, so a later rollback is exact.
  • Overfit check. A proposed text that repeats {{count:config.overfitWords}} consecutive words of a supporting claim gets one retry, then an overfit-risk flag. A rule written around one claim is not a rule.
  • Linking is a second plan: rows can only point at a lesson that exists, so distill.mjs --link runs after the lesson rows are written, and turns the linked rows' cases into contested cases.

In the trial one group qualified: Predictive, Rule should change, rule 1, {{count:end.ls1Supporting}} claims. A Debate group with one Rule unclear claim was skipped.

Promote, in two phases

  1. Preconditions. The lesson is Approved; its Current text still equals the live text (otherwise it is stale); the effective text, Editor wording if filled, is at most {{count:config.maxText}} characters; no other promote is in flight.
  2. Candidate. The rule is replaced in a copy of the rubric, every hash is recomputed and the next version is assigned, under runs/<id>/candidate/.
  3. Judge and decide. The claims behind every gate case plus the canaries, judged under both rulebooks; eval.mjs applies the five conditions and writes the card.
  4. Reconfirm. Every case that flipped, for better or worse, on a tag both rulebooks judge, is judged {{count:config.reconfirmRuns}} more times under each; the verdict after this reconfirmation is the one that counts.
  5. PASS: a plan with the Rulebook row (When to use, Rule version, Tag hash, Changed by), the lesson Live, the card and Rubric in force; plan check and apply accept the Rulebook write only with the evidence of that PASS (decision M14); it is applied and read back; then --finalize copies the candidate to rubric.json and history/, updates the lock and the changelog, activates the lesson's contested cases, and the skill commits. HOLD or FAIL: only the card and the Gate result are written; the candidate folder is marked rolled back.

Rollback (promote.mjs --rollback <lesson> --confirm) is the one path that bypasses the gate, and only for the most recent Live lesson: it restores the previous rubric from history/ byte for byte, checks that the hash matches, and writes a restore plan. It was not exercised in the trial, because nothing went live.

Reconfirmation

Decision M11. With {{count:config.judgeRuns}} runs per rulebook a borderline claim is often decided 2 to 1, and such a claim can flip on noise alone: attempts 1 to 3 were each blocked by borderline cases decided 2 to 1 at confidence 0.5 to 0.65. So a flipped case is judged {{count:config.reconfirmRuns}} more times under each rulebook ({{count:config.reconfirmTotal}} runs in all) and decided again; the card lists every reconfirmed case as confirmed or noise. Fixes and breaks get the same treatment, so a lesson cannot win on noise either. Canaries are not reconfirmed: a canary must pass outright.
