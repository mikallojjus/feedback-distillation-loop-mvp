The loop

In short

  • An editor decides the Tag outcome of a queue row. Only when overruling the agent or the written rule does the editor pick a Why wrong value and write one sentence.
  • Every decision that settles a tag, Applies or Does not apply, becomes a regression case. A decision that blames the rule becomes a contested case: kept, but not binding until the rule is fixed.
  • When decisions on different claims blame the same rule, the agent drafts a lesson: a new text for that one rule. The rule owner approves or rejects it, and may rewrite it.
  • The gate tests the candidate rulebook against the current one on the same claims. Only a PASS lets promote write the new text, as a new rubric version; a follow-up then re-checks the claims behind the lesson.
  • The agent writes only its own columns, through plans that are read back after every write. A changed editor field stops it (the trust breaker), and anyone can pause it with one checkbox.
  • Every result card says small sample: on this little data a PASS would mean no sign of harm, not proof of improvement.

The loop in seven steps

  1. Tag. The agent judges each claim against the rulebook, {{count:config.judgeRuns}} runs per claim, and writes its tags on the claim. Tags it cannot settle go to the editors' queue, at most {{count:config.weeklyCap}} new rows a week.
  2. Decide. An editor sets the Tag outcome of a queue row: Applies, Does not apply, Needs evidence or Ask another editor. When overruling the agent or the written rule, the editor also picks Why wrong and writes one sentence.
  3. Keep. A decision that settles the tag becomes a permanent test. A decision that says the rule is unclear or wrong waits as a contested case until a lesson about that rule goes live.
  4. Distill. When decisions on different claims blame the same rule ({{count:config.minClaims}} claims for Rule unclear, {{count:config.minClaimsRuleChange}} for Rule should change), the distiller drafts a lesson: the smallest new text for that rule that agrees with the editors.
  5. Approve. The rule owner sets Approved or Rejected, and may rewrite the text in Editor wording; that text is then tested instead.
  6. Gate. The agent judges the same claims under the current and the candidate rulebook and compares them. PASS goes live; HOLD and FAIL change nothing and leave a result card.
  7. Follow up. After a PASS the claims behind the lesson are judged again, and their queue rows show Fixed or Still wrong. A decided row never goes back to the queue (decision M12); only undecided rows whose proposal flips return, as Rule changed.

The gate

The gate compares two rulebooks on the same claims: the current one, and a candidate in which the lesson's text replaces the old rule. The claims are those behind every saved regression case, plus every canary. The judge runs {{count:config.judgeRuns}} times under each rulebook, and the verdict per claim and tag is the majority. A change goes live only if all five conditions hold:

#ConditionIn plain wordsIf not
1Every active canary passes under the candidate.The rulebook's own example claims still come out right.FAIL
2No active regression case that passes under the current rules fails under the candidate.No saved editor decision is lost.FAIL
3Every tag with at least {{count:config.minPositives}} labelled positives keeps the lower bound of its paired change in accuracy no lower than −{{count:config.tolerancePoints}} points. A tag with fewer positives whose rules changed: {{count:config.ungatedHold}} wrong-way flip holds, {{count:config.ungatedFail}} fail.No other tag gets measurably worse.FAIL or HOLD
4The target tag's interval lies above zero. Straddling zero holds; at or below zero fails.The lesson does what it claims.HOLD or FAIL
5No tag applied that the candidate does not judge, and no human-only tag.The judge stays in its lane.FAIL

That gives one of three verdicts, PASS, HOLD or FAIL: any failed condition makes it FAIL; otherwise any held condition makes it HOLD; otherwise it is PASS.

Settings for the MVP

  • {{count:config.minPositives}} labelled positives per tag before a tag is gated, instead of the research's 30 (decision M5). The trial has few labels, so every card carries the small-sample label.
  • Intervals come from a paired bootstrap over claims ({{count:config.bootstrap}} resamples, seeded): in plain words, the comparison is repeated many times on reshuffled claims to see how much the result could move, and it is computed the same way every time, so the same judgments always give the same card.
  • Reconfirmation (decision M11): a regression case that flips between the two rulebooks is judged {{count:config.reconfirmRuns}} more times under each ({{count:config.reconfirmTotal}} runs each) before it counts, for fixes and breaks alike. It was added after three attempts were blocked by borderline claims decided 2 to 1, at confidence 0.5 to 0.65, which a few more runs could tip either way.

Plans and read-back

  1. Plan. A script writes runs/<run-id>/plan.jsonl: a header, then one create or update per line, each checked against the allowlist as it is built. Relations are written by name and resolved through the pull's id map; an op may carry expectations about the row it changes.
  2. Check. plan.mjs check --run <id> checks every op again, skips an op whose row changed or was decided meanwhile, turns a create whose key exists into an update, writes the batch files and arms runs/APPLYING.json with the plan's hash.
  3. Apply. apply.mjs --run <id> refuses a plan edited after the check, pulls the touched databases (the pre snapshot), sends the ops through the REST client, records each result in applied.jsonl, then pulls again.
  4. Verify. verify.mjs compares every planned value with the new pull (text normalised, relations as id sets) and the editor-owned fields of every touched row with the pre snapshot. Missing ops go to plan.retry.jsonl (exit 1); a changed editor field writes runs/PAUSED with the field, before and after (exit 5). Rows the plan did not touch are ignored, because editors work while the agent does.

In the trial: {{count:applies}} applies, {{count:opsLanded}} writes landed, {{count:appliesClean}} of {{count:applies}} verified clean, {{count:editorFieldsTouched}} editor fields changed.

Judgment files and the config id

Every judgment is a file: runs/judgments/<config16>/run-<n>/<item>.<text8>.json, one claim in one run against every model-judged tag, with a decision, a confidence, the rule relied on, the trigger phrase and a reason per tag. A ledger.jsonl per configuration records each cell; a crash leaves at most a torn last line, which the next run cuts off.

  • Config id (config16, its first 16 hex digits): a hash over the driver, the model, the effort, the prompt version, the rubric hash, the scope hash and the Claude Code version. A valid cell is never judged again under the same id, which is why every gate's baseline was free and attempt 3 cost nothing.
  • text8: the first 8 hex digits of the hash of the claim's normalised text, so an edited claim has no judgment rather than a stale one.
  • In the trial: current rules {{count:baseline.config}}; candidates {{count:gate.ls1a1.candidate}} (attempt 1), {{count:gate.ls1a2.candidate}} (attempts 2 to 4), {{count:gate.ls1a5.candidate}} (attempt 5) and {{count:gate.ls2.candidate}} (the planted LS-2).

The schema is schemas/judgment.schema.json. Model-judged tags carry basis model; tags decided in code carry deterministic (Unsourced, from the sources count) or no_source_text (the two source-reading tags, which nobody reads in this trial).
