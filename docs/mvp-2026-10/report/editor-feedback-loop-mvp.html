At a glance

In short

The claim tagger now learns from editor decisions through a written rulebook instead of a growing prompt. Its first real lesson was measured, approved and then refused by the gate, for exactly the kind of side effect the gate is there to catch. The live rulebook is unchanged.

  • What exists now. A Notion page, "Editorial feedback loop", with six databases, the views editors and the rule owner work in, and a callout. A repository, geo-agents, with the agent (judge, proposer, distiller, gate, promote, follow-up, status), one skill, /claim-tagger, and 713 unit tests. A real run on 60 claims.
  • What happened. The judge tagged every claim 3 times (180 judgments, 0 errors, $2.06), and 40 uncertain tags went to the editors' queue. An AI persona standing in for an editor decided 10 rows and a reviewer persona 2 more. The distiller turned the 4 "Rule should change" decisions on Predictive rule 1 into one lesson with a proposed rule text, and the rule owner approved it.
  • What the gate did. It judged the candidate rulebook against the current one on the saved regression cases and all 83 canaries, 5 times with 3 wordings, and refused every time. A planted bad lesson was refused for the right reason, no improvement on its own tag, and rolled back.
  • The learning is real and measurable. Under the best wording all four hedged rows flip to the editors' answer, each confirmed over 8 runs: Predictive gains +36.4 points, with a lower bound of +9.1. It did not go live because the same wording, also confirmed over 8 runs, moves one Context-dependent decision on an unrelated claim, and the rule owner ruled that decision right: a real regression.
  • Where that leaves the team. The rulebook is still at rubric version 2026-10-13.1, every refusal has a result card, and the next engineering step is known: a per-tag judge, the item the research kept for interference. See Decisions and next steps.
  • Against the forecast. The research predicted a HOLD for the first lesson, because a handful of hedged forecasts cannot prove a gain. The gain turned out to be measurable; a side effect on another tag is what stopped it.

What the agent learned, and why it is not live

Four decisions say the same thing about Predictive rule 1, which lists "is likely to" as a forecast marker: a hedged claim about a tendency, a comparison of strategies or a trajectory is an assessment of the present, not a forecast. Two came from the 9 October audit, two from the editor persona. The lesson rewrites rule 1 so that a hedged marker fires only on a definite future outcome.

In attempt 4, Predictive accuracy on its labelled claims rises from 54.5% to 90.9%: +36.4 points, with a 95% interval from +9.1 to +63.6. That is a real gain, though on a small sample.

The last row is the problem. The lesson is about forecasts; the Melania Trump claim has nothing to do with them. Yet under the new wording the judge reads Self-contained rule 2 (a pronoun resolved by a name in the same claim keeps it Self-contained) as settling the claim, and stops tagging it Context-dependent. The rule owner ruled that the decision stands: "her initiative" names a kind of thing, not which one, exactly like the rulebook's own example "Open AI's initiative". A change to one rule that moves a decision on another tag is the regression the gate's second condition exists to stop, so the refusal is correct.

What this means. The loop did what it should: editors' reasoning became a rule text, the rule text fixed the rows it was meant to fix, and the gate refused it for a confirmed side effect instead of letting it through. The fix is structural, not more wording: a judge that sees one tag's rules at a time cannot carry a Predictive change into a Context-dependent answer.

The loop

In short

  • An editor decides the Tag outcome of a queue row. Only when overruling the agent or the written rule does the editor pick a Why wrong value and write one sentence.
  • Every decision that settles a tag, Applies or Does not apply, becomes a regression case. A decision that blames the rule becomes a contested case: kept, but not binding until the rule is fixed.
  • When decisions on different claims blame the same rule, the agent drafts a lesson: a new text for that one rule. The rule owner approves or rejects it, and may rewrite it.
  • The gate tests the candidate rulebook against the current one on the same claims. Only a PASS lets promote write the new text, as a new rubric version; a follow-up then re-checks the claims behind the lesson.
  • The agent writes only its own columns, through plans that are read back after every write. A changed editor field stops it (the trust breaker), and anyone can pause it with one checkbox.
  • Every result card says small sample: on this little data a PASS would mean no sign of harm, not proof of improvement.

The loop in seven steps

  1. Tag. The agent judges each claim against the rulebook, 3 runs per claim, and writes its tags on the claim. Tags it cannot settle go to the editors' queue, at most 40 new rows a week.
  2. Decide. An editor sets the Tag outcome of a queue row: Applies, Does not apply, Needs evidence or Ask another editor. When overruling the agent or the written rule, the editor also picks Why wrong and writes one sentence.
  3. Keep. A decision that settles the tag becomes a permanent test. A decision that says the rule is unclear or wrong waits as a contested case until a lesson about that rule goes live.
  4. Distill. When decisions on different claims blame the same rule (2 claims for Rule unclear, 3 for Rule should change), the distiller drafts a lesson: the smallest new text for that rule that agrees with the editors.
  5. Approve. The rule owner sets Approved or Rejected, and may rewrite the text in Editor wording; that text is then tested instead.
  6. Gate. The agent judges the same claims under the current and the candidate rulebook and compares them. PASS goes live; HOLD and FAIL change nothing and leave a result card.
  7. Follow up. After a PASS the claims behind the lesson are judged again, and their queue rows show Fixed or Still wrong. A decided row never goes back to the queue (decision M12); only undecided rows whose proposal flips return, as Rule changed.

The gate

The gate compares two rulebooks on the same claims: the current one, and a candidate in which the lesson's text replaces the old rule. The claims are those behind every saved regression case, plus every canary. The judge runs 3 times under each rulebook, and the verdict per claim and tag is the majority. A change goes live only if all five conditions hold:

#ConditionIn plain wordsIf not
1Every active canary passes under the candidate.The rulebook's own example claims still come out right.FAIL
2No active regression case that passes under the current rules fails under the candidate.No saved editor decision is lost.FAIL
3Every tag with at least 5 labelled positives keeps the lower bound of its paired change in accuracy no lower than −5 points. A tag with fewer positives whose rules changed: 1 wrong-way flip holds, 3 fail.No other tag gets measurably worse.FAIL or HOLD
4The target tag's interval lies above zero. Straddling zero holds; at or below zero fails.The lesson does what it claims.HOLD or FAIL
5No tag applied that the candidate does not judge, and no human-only tag.The judge stays in its lane.FAIL

That gives one of three verdicts, PASS, HOLD or FAIL: any failed condition makes it FAIL; otherwise any held condition makes it HOLD; otherwise it is PASS.

Settings for the MVP

  • 5 labelled positives per tag before a tag is gated, instead of the research's 30 (decision M5). The trial has few labels, so every card carries the small-sample label.
  • Intervals come from a paired bootstrap over claims (1,000 resamples, seeded), so the same judgments always give the same card.
  • Reconfirmation (decision M11): a regression case that flips between the two rulebooks is judged 5 more times under each (8 runs each) before it counts, for fixes and breaks alike. It was added after three attempts were blocked by borderline claims decided 2 to 1, at confidence 0.5 to 0.65, which a few more runs could tip either way.

Plans and read-back

  1. Plan. A script writes runs/<run-id>/plan.jsonl: a header, then one create or update per line, each checked against the allowlist as it is built. Relations are written by name and resolved through the pull's id map; an op may carry expectations about the row it changes.
  2. Check. plan.mjs check --run <id> checks every op again, skips an op whose row changed or was decided meanwhile, turns a create whose key exists into an update, writes the batch files and arms runs/APPLYING.json with the plan's hash.
  3. Apply. apply.mjs --run <id> refuses a plan edited after the check, pulls the touched databases (the pre snapshot), sends the ops through the REST client, records each result in applied.jsonl, then pulls again.
  4. Verify. verify.mjs compares every planned value with the new pull (text normalised, relations as id sets) and the editor-owned fields of every touched row with the pre snapshot. Missing ops go to plan.retry.jsonl (exit 1); a changed editor field writes runs/PAUSED with the field, before and after (exit 5). Rows the plan did not touch are ignored, because editors work while the agent does.

In the trial: 17 applies, 304 writes landed, 17 of 17 verified clean, 0 editor fields changed.

Judgment files and the config id

Every judgment is a file: runs/judgments/<config16>/run-<n>/<item>.<text8>.json, one claim in one run against every model-judged tag, with a decision, a confidence, the rule relied on, the trigger phrase and a reason per tag. A ledger.jsonl per configuration records each cell; a crash leaves at most a torn last line, which the next run cuts off.

  • Config id (config16, its first 16 hex digits): a hash over the driver, the model, the effort, the prompt version, the rubric hash, the scope hash and the Claude Code version. A valid cell is never judged again under the same id, which is why every gate's baseline was free and attempt 3 cost nothing.
  • text8: the first 8 hex digits of the hash of the claim's normalised text, so an edited claim has no judgment rather than a stale one.
  • In the trial: current rules f0b5d66f0b36f8e5; candidates 2165827e059e280c (attempt 1), 038f96ade2a80e70 (attempts 2 to 4), a0d49bb16857dce8 (attempt 5) and 6283ce5782027655 (the planted LS-2).

The schema is schemas/judgment.schema.json. Model-judged tags carry basis model; tags decided in code carry deterministic (Unsourced, from the sources count) or no_source_text (the two source-reading tags, which nobody reads in this trial).

How to decide a row

  1. Read the claim (the row links to it) and "Why I recommend this". Agent confidence runs from 0 to 1 and is not calibrated: it sorts the queue, it is not a probability.
  2. Set Tag outcome yourself, whatever the agent proposed: Applies, Does not apply, Needs evidence (a source must be read first) or Ask another editor. Agreeing with Add tag or Keep tag means Applies; agreeing with Do not add tag or Remove tag means Does not apply.
  3. Only when you overrule the agent or decide against the written rule, pick one Why wrong value:
    • Agent slip: the rule settles it, the agent did not follow it.
    • Rule unclear: the rule does not settle it.
    • Rule should change: the rule settles it but is wrong.
    • No tag fits: no rulebook tag names the problem.
    • Other: none of these.
  4. Write one sentence in Your reasoning for every Why wrong value except Agent slip. Lessons are drafted from these sentences; Needs your note lists the rows that still lack one.

That is all: Stage and Direction update themselves, the agent never changes these fields, and a decided tag is never overwritten on its claim.

What the connector's DDL taught

  • A RELATION takes the bare data-source UUID, not a collection:// link.
  • A unique-id prefix needs at least two characters, so lessons are LS-1, LS-2 rather than L-1.
  • The DDL parser splits formula text at a quote, comma, space, quote sequence: write "," inside a formula without the space after the comma.
  • A formula cannot read a property through a relation (current.prop() is a type error). Tag name and Lesson status are therefore rollups, and the two Claims columns roll up the Applied tag and Rejected tag formulas of the queue rows.
  • Column names avoid apostrophes ("Editor wording", not "Editor's wording"); editor guidance lives in the column descriptions, since there is no start page.

Code and commands

In short

  • Open Claude Code in the geo-agents folder and ask in plain words, for example "run this week's tagging loop, keep it small, tell me what's waiting for me". The skill /claim-tagger picks the steps and answers in a short paragraph.
  • Six subcommands do the work: status (which rulebook is in force, what waits for whom), tag (judge claims, fill the queue), distill (turn decisions into proposed lessons), promote (put an approved lesson through the gate), follow-up (re-check the claims behind a live lesson) and setup (once).
  • Every subcommand is a fixed sequence of scripts. The scripts do every Notion read and write; Claude Code runs them in order, reads their one-line summaries and reports.
  • In this version every write goes through the integration token in .env, so the loop runs where the token is configured; without it the skill stops and says so.
  • The headless test, a fresh session as on an editor's machine, found four things such a machine needs. They are now in the README and the skill.

Pause and resume

  • To pause: tick Paused in Agent settings (one row) and, if you like, say why in Reason. Every subcommand starts with a check that stops when Paused is ticked.
  • When the agent pauses itself: the trust breaker writes a pause file when an editor field changed on a row the agent was writing, and names the field with its value before and after. A person looks at it, then clears it with status.mjs --unpause --confirm, which records who cleared it and when.
  • To resume: untick Paused. A run that stopped half way, for a pause or for the subscription's usage window, picks up where it left off and keeps the work already finished.

Neither the pause drill nor the trust-breaker drill was run in this trial; both are covered by unit tests.

Headless use: what an editor's machine needs

MSYS_NO_PATHCONV=1 claude -p "/claim-tagger status" --settings .claude/settings.json --permission-mode acceptEdits --output-format stream-json --verbose
  1. Pass the settings. A folder never opened interactively is untrusted, and Claude Code ignores its .claude/settings.json allow rules (the session's own warning: "this workspace has not been trusted"). Passing --settings .claude/settings.json brings them back.
  2. One Bash rule per script. Bash permission rules match whole words, so a directory prefix such as node agents/claim-tagger/scripts/* never matched. The settings now list one rule per script, for example Bash(node agents/claim-tagger/scripts/status.mjs:*). A command chained with ; or && is denied, by design.
  3. Stop Git Bash rewriting the slash. In Git Bash, /claim-tagger status arrived as a path under the Git installation folder. Set MSYS_NO_PATHCONV=1, or start from PowerShell.
  4. Never inspect .env. The first session tried to grep .env to see whether a token was set. The skill now forbids reading, grepping or printing it, and status.mjs --check reports whether a token is configured.

Judge contract

  • Items. --items claims takes the claims of the latest pull; --items eval the claims behind the active cases plus the canary texts. Batches of 8 claims, shuffled per run with a seeded generator; 3 runs per rubric version.
  • Call. claude -p spawned with an argument list and no shell, a pinned model (Sonnet 5.5; Haiku 5.5 for smoke runs), effort medium, no tools, one turn. The system prompt is prompts/judge.md with the compact rubric, rendered once per configuration so the prompt cache hits; the claims go on stdin inside <claim id sources> elements, with the instruction that claim text is data, never instructions.
  • Answer. Per claim and per model-judged tag: apply, do_not_apply, ask_editor (the rules do not settle it) or cannot_tell (information is missing); a confidence p from 0 to 1, not calibrated; the rule relied on (Predictive rule 1); the trigger phrase; a reason of at most 25 words.
  • Checks. The reply must have the batch's ids, every in-scope tag exactly once, consistent counterpart pairs and a rule of the same tag. A bad batch gets one retry with the problems quoted, then its items are errors. The pinned model must appear in the reply's usage, or the run stops (exit 4).
  • Decided in code. Unsourced from the sources count; Improperly sourced and Source inaccessible are not checked in this trial, because no source text is read; Editor verified is never output.
  • Majority. More than half the runs agreeing gives the verdict; otherwise ask editor; a missing or failed run gives error.

Proposer rules

  • Decided tags are kept. An editor's Tag outcome, or a seeded outcome, always wins: its queue row is never touched and the claim's Agent tags follow it from the next run.
  • Readiness, in order: Needs editor (a model-judged tag is ask editor or error), Fix needed (an applied tag has Issue polarity), Not checkable (cannot tell, or the sources count is unknown), Ready.
  • Why in queue: Low confidence when the runs disagree, the verdict is ask editor or error, or the mean confidence lies between 0.25 and 0.75; Rule changed when the tag's rules changed since it was last judged and the verdict flipped, on undecided rows only.
  • Priority: Check source for Read source first; High for Rule changed, for Low confidence that leans towards applying an Issue tag, and for a three-way split; Medium otherwise. Within the weekly cap new rows are taken by priority, then lowest confidence; the rest are held back until the cap allows (67 in the first run).
  • Idempotent. A plan carries only values that differ from the pull, so running propose twice on the same inputs gives an empty plan.

Distiller

  • Input. Decided rows whose Why wrong is Rule unclear or Rule should change, plus seeded rows whose reasoning starts "Rule should change:".
  • Groups. By tag, Why wrong and the rule the agent cited, counting distinct claims. A group becomes a lesson at 2 claims for Rule unclear and 3 for Rule should change. A tag that already has a Proposed, Approved or Live lesson only gains supporting rows.
  • One model call per group (Opus 5.5, prompts/distill.md) with the tag's rulebook entry, the group's rows and other decided rows on the tag as counter-evidence. It returns the kind of change, the target rule, a title, a statement, the proposed text, invented boundary examples and the counter-evidence it would flip.
  • Current text always comes from the rubric file, never from the model, so a later rollback is exact.
  • Overfit check. A proposed text that repeats 8 consecutive words of a supporting claim gets one retry, then an overfit-risk flag. A rule written around one claim is not a rule.
  • Linking is a second plan: rows can only point at a lesson that exists, so distill.mjs --link runs after the lesson rows are written, and turns the linked rows' cases into contested cases.

In the trial one group qualified: Predictive, Rule should change, rule 1, 4 claims. A Debate group with one Rule unclear claim was skipped.

Promote, in two phases

  1. Preconditions. The lesson is Approved; its Current text still equals the live text (otherwise it is stale); the effective text, Editor wording if filled, is at most 1,900 characters; no other promote is in flight.
  2. Candidate. The rule is replaced in a copy of the rubric, every hash is recomputed and the next version is assigned, under runs/<id>/candidate/.
  3. Judge and decide. The claims behind every gate case plus the canaries, judged under both rulebooks; eval.mjs applies the five conditions and writes the card.
  4. Reconfirm. Every case that flipped, for better or worse, on a tag both rulebooks judge, is judged 5 more times under each; the verdict after this reconfirmation is the one that counts.
  5. PASS: a plan with the Rulebook row (When to use, Rule version, Tag hash, Changed by), the lesson Live, the card and Rubric in force; plan check and apply accept the Rulebook write only with the evidence of that PASS (decision M14); it is applied and read back; then --finalize copies the candidate to rubric.json and history/, updates the lock and the changelog, activates the lesson's contested cases, and the skill commits. HOLD or FAIL: only the card and the Gate result are written; the candidate folder is marked rolled back.

Rollback (promote.mjs --rollback <lesson> --confirm) is the one path that bypasses the gate, and only for the most recent Live lesson: it restores the previous rubric from history/ byte for byte, checks that the hash matches, and writes a restore plan. It was not exercised in the trial, because nothing went live.

Reconfirmation

Decision M11. With 3 runs per rulebook a borderline claim is often decided 2 to 1, and such a claim can flip on noise alone: attempts 1 to 3 were each blocked by borderline cases decided 2 to 1 at confidence 0.5 to 0.65. So a flipped case is judged 5 more times under each rulebook (8 runs in all) and decided again; the card lists every reconfirmed case as confirmed or noise. Fixes and breaks get the same treatment, so a lesson cannot win on noise either. Canaries are not reconfirmed: a canary must pass outright.

Glossary

Every term marked with * in the report, in plain words. Each tab also lists the terms it uses at its foot.

canary
A claim with a known right answer that the agent must always get right: one of the rulebook's own example claims, or a counter-example on the other side of a tag pair. The trial has 86, of which 83 are active; the others wait for a ruling on forecasts. The baseline and every gate check all active canaries, and one failing canary fails the gate.
config id
The fingerprint of everything that shapes a judgment: the model, the effort setting, the prompt version, the rubric hash, the scope hash, the Claude Code version and the driver. A judgment is reused only under exactly the same config id, which is why a gate's baseline costs nothing once the current rules have been judged.
contested case
A regression case whose decision says the written rule is the problem (Why wrong is Rule unclear or Rule should change). It is kept, but it does not block a gate until a lesson that fixes the rule goes live; for that lesson it counts as one of the rows to fix.
follow-up
The re-check after a rule change goes live. The agent judges the lesson's claims again under the new rules and writes Fixed, Still wrong or Not re-run on each decided row they came from, so editors can see what their decision changed. Not reached in the trial, because no lesson went live.
gate
The test a rule change must pass before it goes live. The agent judges the same claims under the current and the candidate rules and compares them: every canary and every saved regression case that passed before must still pass, no tag with enough labelled examples may get measurably worse, and the tag the lesson targets must improve. The result is PASS, HOLD or FAIL, written on a result card.
interference
A rule change on one tag that moves the agent's answer on another tag, on a claim the lesson is not about. The judge reads the whole rulebook at once, so new wording in one rule can tip a borderline call elsewhere. In the trial the best wording of the Predictive lesson also flipped the agent's answer on a Context-dependent claim, confirmed over 8 runs, and the gate refused it.
lesson
What editor decisions teach about a rule, written so that it holds for claims nobody has seen yet. The agent drafts a lesson in the Rule changes database when decisions on different claims point the same way. A lesson changes the rulebook only after the rule owner approves it and it passes the gate; it is never pasted into the agent's prompt. Lesson ids start with LS.
PASS / HOLD / FAIL
The three verdicts of the gate, written on every result card. PASS: the change improved the tag it targets and broke nothing, so it can go live. HOLD: the evidence is too thin to tell whether it helped, so the rulebook stays as it is and the lesson waits for more labelled claims. FAIL: the change broke something that worked, or did not help its own tag; the rulebook keeps its text. A real lesson stays Approved after a FAIL so it can be reworded and tested again; the planted test was marked Rolled back.
per-tag judge
A judge that sees one tag's rules at a time, or one tag pair's, so a change to one tag's rules cannot move another tag's answer. The research kept it for weeks 7 to 12 (its package C), to be built if tests showed interference; the trial showed it, so it is the next engineering step.
promote
To take an approved lesson through the gate and, if it passes, write its text into the rulebook and mark the lesson Live (the /claim-tagger promote command). On HOLD or FAIL nothing is written to the rulebook, and the result card says why. A promoted rule can be rolled back exactly, because the previous text and version are kept.
read-back
The check after every write: the scripts pull the databases they touched again, compare each planned value with what Notion now shows, and compare the editor-owned fields of every touched row with their values before the write. A run counts as done only when every write landed and no editor field changed.
reconfirmation
A second look at a regression case that flipped between the current and the candidate rules. Before the flip counts, both rulebooks judge that claim 5 more times (8 runs each), and the card marks the flip confirmed or noise. Fixes and breaks are held to the same standard. Added during the trial as decision M11.
regression case
One claim, one tag and the answer an editor decided, kept as a permanent test. Before a rule change goes live the agent runs every active case again; one that passed before and fails after is a regression, and it fails the gate.
rubric version
The version label of the rulebook the agent used, written like 2026-10-13.1. Every rule change that goes live creates a new version, and every run, queue row and result card records the version it used, so any tag can be traced to the exact rules that produced it. The live version stayed 2026-10-13.1 throughout the trial; each candidate was labelled 2026-10-13.2.
rulebook
The Notion database that holds the rules the agent tags by: one row per tag, with its description, numbered "When to use" rules and example claims. Its twin on disk, rubric.json, carries a hash per rule, per tag and for the whole rubric. The agent reads it before each run and changes it only when an approved lesson passes the gate.
seeded outcome
A decision copied once from the 9 October audit into an agent-owned column, Seeded outcome (with Seeded reasoning and Seeded at), so that no script ever writes the editor's own Tag outcome. A row's Effective outcome is its Tag outcome when an editor set one, otherwise its seeded outcome.
small sample
A label on every result card, because the trial has few labelled claims. The gate asks for at least 5 labelled examples of a tag instead of the research's 30 before it judges that tag's accuracy, so a PASS would mean no sign of harm on the claims tested, not proof that the rule is better everywhere.
Tag outcome
An editor's decision on one claim and one tag: Applies, Does not apply, Needs evidence or Ask another editor. It is the editor's own field. The agent never writes it, and a decided tag is never overwritten.
trust breaker
A check that stops the agent when an editor's work might have been touched. After every write the agent compares the editor-owned fields on the rows it changed with a snapshot taken before; any difference writes a pause file naming the field with its before and after values. A person looks, then clears the pause.
Why wrong
The reason an editor gives when overruling the agent or deciding against the written rule: Agent slip, Rule unclear, Rule should change, No tag fits or Other. Each value sends the fix somewhere different: a test, a wording change, a rule change or a new tag. Every value except Agent slip asks for one sentence of reasoning.
