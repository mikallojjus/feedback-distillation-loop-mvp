# The practice page: template, fixed format and what `verify` checks

The page is built from `agents/claim-tagger-mvp/walkthrough/page.md` (repository Markdown) by `walkthrough.mjs start`, through `scripts/lib/notion-blocks.mjs`. Placeholders: `{{edition}}` and `{{date}}` are text the builder fills; `{{view:Your queue}}` and `{{view:Lessons waiting}}` mark where the two linked views go (under the last line of "Doing the work" of steps 3 and 5: in step 3 that is the second numbered list, in step 5 the Doing the work line itself); `{{tables}}` marks where the five inline tables sit (after step 7); `{{help}}` marks the Help toggle, whose content is the `## Help` section at the end of the file.

## Layout, top to bottom

1. A callout whose first line is exactly: "You type four commands yourself (status, tag, distill and promote); the follow-up runs by itself after a PASS, and the engineer sets things up and fixes what breaks."
2. The story: two sentences, a three-row table (Claim, Rule 3 read strictly, The editor), one sentence, and the line "The press pool claim was picked for the demo: the agent is fairly sure of it, but the page marks it To review, so its Agent status reads Waits for you and it sits in Your queue like the AI Force claim, which the agent reads differently from run to run and which the page also marks To review. For real, a claim waits when someone marks it To review or when the agent is unsure." (lint rule g needs the words "picked for the demo")
3. Steps 1 to 7 as headings "Step n · <title>", each with the four bold labels in order: Goal of the step, Existing status, Doing the work, Explaining the outputs. "Doing the work" of step 3 is two numbered lists, one per claim (a bold label, then four lines: Verified tags, Why wrong, Challenged tags notes, Review status), the sentence for Challenged tags notes on a line of its own inside its item (a list line that ends with a backslash keeps the line break before the indented line under it); the lines are the manifest's `enter` values word for word, in the manifest's order, and the text says that a decided claim stays in Your queue until the agent reads it again (the follow-up of step 7). "Explaining the outputs" shows one small table per affected table, with a bold caption naming it, at most four columns and cells of at most 100 characters, claims shortened to about 60 characters (step 2 has two tables under the one caption **Claims**, because the agent's seven columns and Geo Name do not fit in four: Geo Name, Agent tags, Agent confidence and Agent status for all seven claims, then Geo Name, Tags waiting and Agent reasons for the two that wait; step 3 shows Geo Name, Verified tags, Review status and Why wrong, and step 7 Geo Name, Agent tags, Agent status and Agent edition). Step 2 shows what the tag step can write and no more: the Agent reasons rows are one run's reading, in the form propose writes ("<reason> · <rule, when one is cited> · <k> of <n> runs agree"). A claim the agent is sure of is read once, so its line ends "1 of 1 runs agree"; a second reading is made only for a claim the agent is unsure of, a third only when the first two disagree, so "3 of 3" is never shown and the page never says that three readings are made. The press pool line cites rule 3; the AI Force line is Can't tell, which cites no rule here, and the text under the tables says that the figures differ from run to run, that the agent may read the AI Force claim as Can't tell or answer with confidence either way, and that both claims wait whatever the reading (both are To review). A test in `tests/mvp/propose.test.mjs` reads these rows from the page. Step 7 says in one line that only the two decided claims name the new edition and the five earlier decisions keep theirs until the next tag run, that Agent confidence follows the new reading (the follow-up writes it) and that Agent status reads Done on both, so both have left Your queue. Agent notes is nowhere on the page. No step affects Tag decisions, so no step captions it. Step 1 explains an edition in one line. Step 7 has nothing to type and ends with the three lines on what the full version adds later and "Archive this page by hand when you no longer need it."
4. "The tables": the six-line list (the Tag decisions line is "the agent's own record of each decision; nothing to do here", and the page says no more of the ledger), then the five inline tables: Rulebook, Claims, Tag decisions, Rule changes, Agent settings.
5. Help, one toggle: the Why wrong table (a header and four value rows, two columns), the words list (exactly ten entries; Agent status and Verified tags are among them, and Why wrong is not, because the table above it explains each value), and "If something stops" (exactly three lines).

The five view names are production's: Your queue (linked in step 3; a view of the Claims table that lists the claims whose Agent status is Waits for you, lowest confidence first, with no condition on Review status: a claim the editor has decided stays until the agent reads it again), Lessons waiting (linked in step 5, wrapping on), Needs your note and Agent disagreed (tabs of the Claims table), Rulebook (a tab of Rulebook that hides Counterpart). The two views of the ledger ("Your queue (ledger)" and "Needs your note (ledger)") are not on a practice page. The page lint (rule l) knows the five names. Both claims of the editor are created To review, and every judged tag of a claim that is To review waits whatever the confidence, so after the tag step both are in Your queue (Agent tags stays empty on both, Agent status reads Waits for you and Tags waiting holds the tag); step 2 and step 3 say so. The Claims table shows its columns in one order on its own view and on the three views of the Claims: Geo Name, Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Verified tags, Review status, Why wrong, Challenged tags notes, then (own view only) the other Geo columns; the builder sets the own view after the views are made (`arrangeOwnViews`), because the relations are added last and would otherwise come last.

## Words

Page text is for the editor: no time estimates (no minutes, hours, days, weeks, seconds; say "a short wait" and "the longest wait of the seven steps"), no shorthand codes (nothing like D7, R12, C20, ED-4, "answer 4", G1), and never the words gate, rubric, canary, regression, database, subagent, API, mirror or sandbox (say safety check, rulebook, example claim, earlier decision, table, agent, Notion, practice page). Retired names that must not appear: the old view names "Decide these rows" and "Approve this change", the old column names "Gate result" and "Rubric in force", and the old Agent notes prefixes "Fix needed" and "Ready". Banned phrases: "leave these", "leave them", "undecided", "may differ", "most likely", "column guide", "copy this", "you can ignore", "note its". Text quoted from a claim is exempt (a claim may say G20).

## What `W verify` checks

On the page (also on `preview.md` for a dry run): the seven step headings with the four labels in order; every table at most four columns and 100 characters per cell; no banned phrase, engineering word, retired name, time estimate or code; the callout's first line; the "picked for the demo" line; the edition line in step 1; the three closing lines and the archive line in step 7; the Help toggle's three pieces with their exact counts; every affected table captioned in its step and Agent settings in step 6 only; exactly the two linked views (or none, with the no-views fallback recorded in `demo.json`), and only the five view names.

In the tables: five inline tables with the practice titles; Rulebook 1 row, Context-dependent, Status Verified, with the taxonomy's columns; Claims 7 rows with the Geo columns as the manifest has them and the agent's seven columns (Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks) empty at creation; the five decided claims Reviewed with their verified tags (the relation points at the Rulebook row of this page), Why wrong and Challenged tags notes as the manifest has them, always (a changed decided claim is a difference, whatever has run since); the two open claims To review with the other three editor columns empty while no command has run, and in any state once one has (the editor decides them); the Claims table has exactly the structure's live columns (the two "(old)" columns of the first build are never made on a practice page), including the three relations (Agent tags, Tags waiting, Verified tags), whose target is this page's Rulebook; the table's own view and the three views of the Claims show the columns in the order above, and the three views carry the filters of the structure; Tag decisions exactly 5 rows on Context-dependent (the decided claims: Agent proposal, Tag outcome, Why wrong and Your reasoning as the tag step copies a decision, Decided under empty) while no command has run, and no row for an open claim until the tag step makes it; Rule changes empty with the column Safety check result; Agent settings 1 row with Rulebook edition set and no Last run summary (so that status says "none yet", as the table of step 1 does).

In the profile: the rulebook holds the one judged tag, and its edition is the page's edition or a later one whose history still holds the page's edition (a passed safety check moves the rulebook on; the page keeps naming the edition it was built with).

`W verify` reads the page once nothing has run as "fresh" (Last run summary empty and no editor action other than an unchanged one) and holds the open claims and the ledger to their first state only then. `W verify --json` prints `{ ok, problems, counts }`; the walkthrough's evals grade with it.
