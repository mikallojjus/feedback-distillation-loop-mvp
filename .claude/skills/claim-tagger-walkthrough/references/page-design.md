# The practice page: template, fixed format and what `verify` checks

The page is built from `agents/claim-tagger-mvp/walkthrough/page.md` (repository Markdown) by `walkthrough.mjs start`, through `scripts/lib/notion-blocks.mjs`. Placeholders: `{{edition}}` and `{{date}}` are text the builder fills; `{{view:Your queue}}` and `{{view:Lessons waiting}}` mark where the two linked views go (under the last line of "Doing the work" of steps 3 and 5: in step 3 that is the sentence about reason words under the four lists, in step 5 the Doing the work line itself); `{{tables}}` marks where the five inline tables sit (after step 7); `{{help}}` marks the Help toggle, whose content is the `## Help` section at the end of the file.

## Layout, top to bottom

1. A callout whose first line is exactly: "You type four commands yourself (status, tag, distill and promote); the follow-up runs by itself after a PASS, and the engineer sets things up and fixes what breaks."
2. The story: two sentences, a four-row table (Claim, Rule 3 read strictly, The editor) with the four claims of the editor, one paragraph that says the ways a decision can go (the press pool and the AI Force blame rule 3, the USPS claim blames the agent, on the Georgia claim the editor agrees), and the line "The four claims were picked for the demo: the agent is fairly sure of three of them, but the page marks all four To review, so their Agent status reads Waits for you and all four sit in Your queue. The AI Force claim is the one the agent reads differently from run to run. For real, a claim waits when someone marks it To review or when the agent is unsure." (lint rule g needs the words "picked for the demo")
3. Steps 1 to 7 as headings "Step n · <title>", each with the four bold labels in order: Goal of the step, Existing status, Doing the work, Explaining the outputs. "Doing the work" of step 3 is four numbered lists, one per claim, in the order of Your queue (the AI Force claim first, then the press pool, USPS and Georgia claims; a bold label, then three lines: Verified tags, Challenged tags notes, Review status), the sentence for Challenged tags notes on a line of its own inside its item (a list line that ends with a backslash keeps the line break before the indented line under it; the Georgia list has an empty note and says in words that an empty note is a decision too); the lines are the manifest's `enter` values word for word, in the manifest's order, and the text says that a decided claim stays in Your queue until the agent reads it again (the follow-up of step 7, for the claims the rule change rests on). Under the lists one sentence says that a note that starts with "Agent slip.", "Rule unclear." or "Rule should change." is taken as it stands and the agent does not read that tag. The editor is never asked to say why the agent was wrong. "Explaining the outputs" shows one small table per affected table, with a bold caption naming it, at most four columns and cells of at most 100 characters, claims shortened to about 60 characters (step 2 has two tables under the one caption **Claims**, because the agent's columns and Geo Name do not fit in four: Geo Name, Agent tags, Agent confidence and Agent status for all nine claims, then Geo Name, Tags waiting and Agent reasons for the four that wait; step 3 shows Geo Name, Verified tags, Review status and the start of Challenged tags notes for the four; step 4 shows Geo Name and Agent reading for the four, then the **Rule changes** table; step 7 shows Geo Name, Agent tags, Agent status and Agent edition for the four). Step 2 shows what the tag step can write and no more: the Agent reasons rows are one run's reading, in the form propose writes ("<reason> · <rule, when one is cited> · <k> of <n> runs agree"). A claim the agent is sure of is read once, so its line ends "1 of 1 runs agree"; a second reading is made only for a claim the agent is unsure of, a third only when the first two disagree, so "3 of 3" is never shown and the page never says that three readings are made. The press pool line cites rule 3; the AI Force line is Can't tell, which cites no rule here, and the text under the tables says that the figures differ from run to run, that the agent may read the AI Force claim as Can't tell or answer with confidence either way, that all four claims wait whatever the reading (they are all To review), and that Agent reading stays empty on them until step 4. A test in `tests/mvp/propose.test.mjs` reads these rows from the page. Step 4 explains in three sentences what a reading is (Agent slip, Rule unclear, Rule should change, the rule it points at, one line of why) and that only the readings that blame the rule become a draft, and shows the four Agent reading lines the way the Claims table shows them: "Context-dependent: Rule unclear, rule 3 · <a short example note>" for the press pool and the AI Force claim (with a sentence that the agent may read them as Rule should change instead and the draft is the same), "Context-dependent: Agent slip, rule 5 · Your note says so." for the USPS claim and "Nothing to read: the agent agreed with you." for the Georgia claim. Step 7 says that only the claims the rule change rests on (the press pool and the AI Force claim) are re-checked and name the new edition, that the USPS and Georgia claims keep Waits for you until the next tag run, that Agent confidence follows the new reading (the follow-up writes it) and that Agent status reads Done on the two, so both have left Your queue. Agent notes is nowhere on the page. No step affects Tag decisions, so no step captions it. Step 1 explains an edition in one line. Step 7 has nothing to type and ends with the three lines on what the full version adds later and "Archive this page by hand when you no longer need it."
4. "The tables": the six-line list (the Tag decisions line is "the agent's own record of each decision; nothing to do here", and the page says no more of the ledger), then the five inline tables: Rulebook, Claims, Tag decisions, Rule changes, Agent settings.
5. Help, one toggle: the Agent reading table (a header and four value rows, two columns: Agent slip, Rule unclear, Rule should change and "(nothing to read)" for a decision the agent agrees with), one sentence on the reason word, the words list (exactly ten entries; Agent status and Verified tags are among them, and Agent reading is not, because the table above it explains each value; the Views entry describes Needs your note as "the claims the agent read without a note from you"), and "If something stops" (exactly three lines).

The five view names are production's: Your queue (linked in step 3; a view of the Claims table that lists the claims whose Agent status is Waits for you, lowest confidence first, with no condition on Review status: a claim the editor has decided stays until the agent reads it again), Lessons waiting (linked in step 5, wrapping on), Needs your note (a tab of the Claims table: the claims whose Agent reading contains "without your note", so the claims the agent read although the editor wrote no note) and Agent disagreed (a tab), Rulebook (a tab of Rulebook that hides Counterpart). The two views of the ledger ("Your queue (ledger)" and "Needs your note (ledger)") are not on a practice page. The page lint (rule l) knows the five names. The four claims of the editor are created To review, and every judged tag of a claim that is To review waits whatever the confidence, so after the tag step all four are in Your queue (Agent tags stays empty on them, Agent status reads Waits for you and Tags waiting holds the tag); step 2 and step 3 say so. The Claims table shows its columns in one order on its own view and on the three views of the Claims: Geo Name, Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Agent reading, Verified tags, Review status, Challenged tags notes, then (own view only) the other Geo columns; the builder sets the own view after the views are made (`arrangeOwnViews`), because the relations are added last and would otherwise come last.

## Words

Page text is for the editor: no time estimates (no minutes, hours, days, weeks, seconds; say "a short wait" and "the longest wait of the seven steps"), no shorthand codes (nothing like D7, R12, C20, ED-4, "answer 4", G1), and never the words gate, rubric, canary, regression, database, subagent, API, mirror or sandbox (say safety check, rulebook, example claim, earlier decision, table, agent, Notion, practice page). Retired names that must not appear: the old view names "Decide these rows" and "Approve this change", the old column names "Gate result" and "Rubric in force", and the old Agent notes prefixes "Fix needed" and "Ready". Banned phrases: "leave these", "leave them", "undecided", "may differ", "most likely", "column guide", "copy this", "you can ignore", "note its". Text quoted from a claim is exempt (a claim may say G20). The page never says "two claims" or "your 2" for the editor's claims (there are four) and never names the old column that said why the agent was wrong.

## What `W verify` checks

On the page (also on `preview.md` for a dry run): the seven step headings with the four labels in order; every table at most four columns and 100 characters per cell; no banned phrase, engineering word, retired name, time estimate or code; the callout's first line; the "picked for the demo" line; the edition line in step 1; the three closing lines and the archive line in step 7; the Help toggle's pieces with their exact counts and the Agent reading table's four values; every affected table captioned in its step and Agent settings in step 6 only; exactly the two linked views (or none, with the no-views fallback recorded in `demo.json`), and only the five view names.

In the tables: five inline tables with the practice titles; Rulebook 1 row, Context-dependent, Status Verified, with the taxonomy's columns; Claims 9 rows with the Geo columns as the manifest has them and the agent's eight columns (Agent tags, Agent confidence, Agent reasons, Agent status, Tags waiting, Agent edition, Agent remarks, Agent reading) empty at creation, except the Agent reading of the five decided claims, which is their seeded reading ("Context-dependent: Agent slip · Seeded from the audit of 9 October."); the five decided claims Reviewed with their verified tags (the relation points at the Rulebook row of this page) and Challenged tags notes as the manifest has them, always (a changed decided claim is a difference, whatever has run since); the four open claims To review with the other two editor columns empty and an empty Agent reading while no command has run, and in any state once one has (the editor decides them); the Claims table has exactly the structure's live columns (the "(old)" columns of the first builds are never made on a practice page), including the three relations (Agent tags, Tags waiting, Verified tags), whose target is this page's Rulebook; the table's own view and the three views of the Claims show the columns in the order above, and the three views carry the filters of the structure, which are the ones the manifest expects (`expect.claims_view_filters` and `expect.claims_columns`); Tag decisions exactly 5 rows on Context-dependent while no command has run (the decided claims: Agent proposal, Tag outcome and Your reasoning as the tag step copies a decision, the Rulebook edition of the page, Agent reading "Agent slip", Reading note "Seeded from the audit of 9 October." and a Read under that distill sees as current, Decided under empty until the first tag step), and no row for an open claim until the tag step makes it; Rule changes empty with the column Safety check result; Agent settings 1 row with Rulebook edition set and no Last run summary (so that status says "none yet", as the table of step 1 does). The counts the manifest expects (`expect`: 9 claims, 5 decided, 4 open, 5 ledger rows) are checked against the manifest's own lists.

In the profile: the rulebook holds the one judged tag, and its edition is the page's edition or a later one whose history still holds the page's edition (a passed safety check moves the rulebook on; the page keeps naming the edition it was built with).

`W verify` reads the page once nothing has run as "fresh" (Last run summary empty and no editor action other than an unchanged one) and holds the open claims and the seeded readings on the ledger and on the decided claims to their first state only then (the agent reads again after a change of rule, so a reading is the agent's to change once a command has run). `W verify --json` prints `{ ok, problems, counts }`; the walkthrough's evals grade with it.
