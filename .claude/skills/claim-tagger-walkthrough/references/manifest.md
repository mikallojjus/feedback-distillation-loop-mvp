# The manifest: what a practice page holds, how to change it, and the calibration

File: `agents/claim-tagger-mvp/walkthrough/manifest.json`. Every practice page is built from it; `walkthrough.mjs start` reads it (or `--manifest <path>`). Current version: 2026-10-22.1 (the page changed shape on 16 October: editors decide on the Claims table, Tag decisions is the agent's ledger; on 21 October, the feedback round: the agent writes seven columns of its own on the Claims, the editor's tags column is Verified tags, Your queue lists the claims whose Agent status is Waits for you, and step 3 is a numbered list per claim; and on 22 October, the reading round: the editor fills three columns, the agent reads each decision itself into Agent reading, and the editor has four claims to decide instead of two; `calibration.status` is `pending` until three fresh pages, runs 6 to 8, have been run through the new shape. Runs 1 to 5 belong to the earlier versions and are kept).

## Content

- `tag`: the real Context-dependent row of the taxonomy (Name, Description, When to use with its five rules, Example Claims, Counterpart Self-contained, Category, Polarity, Status Verified, Work tags, Geo Status, Geo Tag ID, Evidence, Verified on, `copied_from`). The practice page's Rulebook has this one row.
- `counterpart`: the Self-contained row, kept for its example claims only (it is not on the page).
- `canaries`: the ten example claims the safety check reads: the six of Context-dependent (expected to apply) and four of the five of Self-contained (expected not to apply). `canaries_note` says why the fifth, the domestic-chips claim, is left out: under the rulebook in force the judge reads it Applies at 0.3 to 0.8, so it would fail a safety check for reasons that have nothing to do with the editor's lesson. The builder adds `"tag": "Context-dependent"` when it writes `evals/canaries.jsonl`.
- `claims`: the nine real claims, the four of the editor first, in story order, with the thirteen Geo columns from the dry run of the real table (`key`: presspool, aiforce, usps, georgia, cnn, dallas, contractor, kennedy, stopgap; `short`: the claim cut to about 60 characters). The USPS ballot portal and Georgia entries are the whole entries of the dry run of 15 October (`runs/dry-run/dry-1/rows.jsonl`).
- `decided`: the five claims an editor has Reviewed (cnn and dallas have the tag; contractor, kennedy and stopgap do not). Each entry describes the claim as the page creates it, by the columns of the Claims table: `Verified tags` (a list of tag names; the builder turns it into the relation to the page's Rulebook row), `Review status` (Reviewed) and `Challenged tags notes` (the editor's reasoning from the audit of 9 October, "From the audit of 9 October: ..."; the one-time seeding exception of hard rule 1, which the plan check allows on a create while the page's `runs/SETUP` marker exists; the plan check keys on the prefix, so keep it). There is no Why wrong: an entry that has one, or an `enter` that has one, is "an older shape" and the loader refuses it. Every note ends with a full stop. Where the audit recorded no reasoning (cnn, dallas, kennedy) the note says which way the editor went against the agent's answer, never "the editor agreed": "the editor confirmed this tag, which the agent had read the other way; no reasoning was recorded." (cnn, dallas) and "the editor did not confirm this tag, which the agent had applied; no reasoning was recorded." (kennedy). The real rows in production keep the migration's text ("the editor agreed with the auditor; no reasoning was recorded."); they are the editors' now and are not rewritten. `Agent proposal` is the agent's pre-audit answer: it goes to the claim's row in Tag decisions, together with the outcome and the reasoning copied from the claim (worked out the way the tag step copies a decision; Decided under stays empty). All five decided claims differ from the agent's answer, so the page makes each ledger row already read (decision 73): Agent reading "Agent slip", Reading note "Seeded from the audit of 9 October.", Read under with the key that distill computes for the row (so the first distill reads none of them; the key holds the Rulebook edition of the row, which each seeded row carries and which is the edition of the page), and Rule empty because the seeded row carries no Agent reason; the claim itself is created with its Agent reading, "Context-dependent: Agent slip · Seeded from the audit of 9 October." A decided row where the agent was right would get no reading columns and the claim line "Nothing to read: the agent agreed with you." The ledger has a row for each of these five claims and none for the four open ones.
- `open`: the four claims the editor decides at step 3, all on Context-dependent. `presspool` (the agent says Applies; the editor: the tag does not apply, so nothing is verified; the note says rule 3 does not settle a group every reader knows by its standing role) and `aiforce` (the agent reads it differently from run to run: Can't tell, or a confident answer either way, with or without a rule cited, and the page says so; the editor: Context-dependent verified; the note says rule 3 does not settle a capitalised phrase that names no known body): the agent reads both as a rule problem on rule 3 (Rule unclear, or Rule should change: `expect_reading` accepts both) and the draft rests on them. `usps` (the whole claim from the dry run; the agent proposes Applies at 0.75 or more; the editor: Does not apply, with the note "Agent slip. USPS names which portal, so rule 5 already settles it."): the reason word makes the reading verbatim, no call to the model, Agent slip on rule 5, note "Your note says so." `georgia` (the agent proposes Does not apply, as the audit editor did; the editor agrees: nothing verified, an empty note, `agrees: true`): there is nothing to read, and the claim's Agent reading says "Nothing to read: the agent agreed with you." All four are created with `Review status` "To review" and the other two editor columns empty. `enter` holds what the editor types, word for word and in the order the page gives it: `Verified tags` as a list of tag names (empty for presspool, usps and georgia, `["Context-dependent"]` for aiforce), `Challenged tags notes` (empty for georgia, which the loader allows only with `agrees: true`) and, last because it closes the claim, `Review status` "Reviewed"; `walkthrough.mjs decide --claim <key>` writes exactly these three columns, and `decide --outcome` alone writes an empty note. `calibrate` is what the calibration expects from the agent at step 2. `expect_reading` is what the reading step makes of the claim: `source` (`model`, `verbatim` or `none`), `reading` (the accepted readings, or null for none) and `rule`.
- `alternates`: claims that can replace an open row if the calibration fails on it (the two Fairford withdrawal claims, judged Applies at 0.80 to 0.93; Melania for the USPS claim; a Fairford claim for Georgia, with the editor agreeing on Applies), and the retired rows with the reason each left the story: Melania (decision 33), COVID-19 (decision 37). The USPS ballot portal and Georgia claims were alternates until decision 75 put them in the story.
- `views`: Your queue in step 3 (a view of the Claims table), Lessons waiting in step 5. `expect`: the counts a fresh page has (`rulebook_rows`, `claims`: 9, `ledger_rows`: 5, `reviewed_claims`: 5, `open_claims`: 4, `linked_views`, `tab_views`), the three views of the Claims table (`claims_views`) with their filters (`claims_view_filters`: Your queue is Agent status is Waits for you, Needs your note is Agent reading contains without your note, Agent disagreed is Agent status is Disagrees with your decision), the order of the Claims columns on its own view and on the three views (`claims_columns`: Geo Name, the agent's eight, the editor's three, with Agent reading after Agent remarks), `readings` (what step 4 does: `read` 3, `model_calls` 1, `verbatim` 1, `agree` 1) and the rule the lesson is on. `steps`: the seven steps with their commands and the tables they affect (step 4 affects Claims and Rule changes). `quiet_columns`: Agent settings' Last run summary, rewritten by every command and not required in the step tables.
- `calibration`: `status` (`pending` or `frozen`), a `note` and `runs` (one entry per calibration run: date, manifest version, demo id and page, the agent's answer per open row, how the earlier decisions and the example claims came out, the lesson, the verdicts of every safety check, the outcome).

## Changing it

Change a claim only by replacing the whole entry (the Geo columns come from the dry run of the real table, `runs/dry-run/<id>/rows.jsonl`, so Geo Sources keeps its links). Keep the story: four open claims on one tag, each showing a way a decision can be read (two that blame rule 3, one the editor marks as the agent's slip with a reason word, one the editor agrees on); five decided claims that cover both outcomes; the example claims the judge gets right under the rulebook in force. Change the page text in `page.md` to match: the shortened claims appear in every step table, the lists of step 3 (one numbered list per claim, one column per line, the sentence for `Challenged tags notes` on a line of its own, Georgia's empty note said in words) must be the manifest's `enter` values word for word and in the order of `enter` (a test compares them), and the rule number appears in the callout, the step 4 heading and steps 3 to 7. Bump `manifest_version`, set `calibration.status` back to `pending`, and record why a row left in `alternates`.

## Calibration (before a manifest version ships)

Three fresh practice pages run end to end under the Demos sub-page, entering the manifest's decisions at steps 3 and 5 through `walkthrough.mjs decide` (the three editor columns of a claim) and `approve`. The manifest is frozen when all of these hold, in at least two of the three runs (Georgia in all three): the press pool row gets Applies at a probability of 0.75 or more, citing rule 3; the AI Force row gets Can't tell or Applies at 0.70 or less; the USPS row gets Applies at 0.75 or more; the Georgia row gets Does not apply at 0.25 or less; every earlier decision and every example claim comes out as expected in every run; after step 2 all four open claims (created To review) have empty Agent tags, Agent status Waits for you, one tag in Tags waiting and an empty Agent reading, so all four are in Your queue and `status` says 4 rows wait; after step 3 `status` says 4 rows are decided and waiting, with 3 decisions to read; distill makes one reading call, reads the press pool and the AI Force row as Rule unclear (or Rule should change) on rule 3, reads the USPS row verbatim as Agent slip, reads nothing on Georgia, and drafts exactly one rule change, on Context-dependent rule 3, resting on the press pool and the AI Force claim; at least two of the three safety checks PASS on the draft itself, and any FAIL proposes a whole Editor wording text that quotes the claim it names; the follow-up marks the two rule rows Fixed and neither USPS nor Georgia, and `W where` says the demo is complete. Otherwise swap the failing row for an alternate (the row that leaves becomes an earlier decision or an alternate with a note) and repeat. Each run is recorded in `calibration.runs`.

What the earlier versions showed (runs 1 to 4): a row the judge reads both ways between runs (COVID-19, Applies at 0.80 or Does not apply at 0.25) breaks the story in the run where the disagreement vanishes; a lesson placed on a rule the agent did not cite (rule 4, while the press pool row cites rule 3) never flipped the row on the first safety check, and passed only after the editor's wording; an example claim the judge cannot settle under the rulebook in force (the domestic-chips claim) fails a check that has nothing to do with the lesson.
